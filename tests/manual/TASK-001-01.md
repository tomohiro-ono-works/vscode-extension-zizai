## 準備と起動

1. 対象ブランチ `spike/task-001-01-notebook-ui` を取得し、`git rev-parse HEAD` と `git status --short` を控える。結果の対象commitはTaskの実施記録／今回の引き渡しを参照する。未コミット差分があれば併記する。
2. 対象IDEでリポジトリ直下をフォルダーとして開く。信頼済みの検証用フォルダーで行う。Node.jsがターミナルから利用でき、Jupyter／Python拡張とPythonカーネルが対象IDEのExtension Development Hostで利用できることを確認する。
3. 両IDEのバージョン情報と拡張一覧の版を控える。VS CodeではCLIの `code --version`、`code --list-extensions --show-versions` も利用可能。KiroではCLIが使えれば `kiro --version`、`kiro --list-extensions --show-versions`、使えなければ画面から取得する。
4. 「実行とデバッグ」で **TASK-001-01: Stable API control (PROTOTYPE)** を選びF5。preLaunchTaskが `dist/stable/` を準備する。別のExtension Development Hostが起動する。以降のコマンドはその別ウィンドウで実行する。
5. Stableの確認後、デバッグを停止して別Hostを閉じる。次に **TASK-001-01: editorInsets proposed (PROTOTYPE)** を選びF5。こちらは `dist/insets/` と `--enable-proposed-api=zizai-lab.task-001-01-probe` を使用する。API許可のエラーがあれば全文を記録する。
6. VS CodeとKiroの両方で4〜5を独立して繰り返す。`${execPath}` で実行中IDEを起動する設定だが、Kiroのデバッグ対応も未検証なので起動したアプリ名を必ず確認する。

F5を利用できない場合のCLI例（リポジトリ直下、各コマンドを個別に実行）：

```sh
node tests/notebook-ui-gate/prepare.mjs stable
code --new-window --extensionDevelopmentPath=./tests/notebook-ui-gate/dist/stable
node tests/notebook-ui-gate/prepare.mjs insets
code --new-window --extensionDevelopmentPath=./tests/notebook-ui-gate/dist/insets --enable-proposed-api=zizai-lab.task-001-01-probe
```

Kiroでは `code` を `kiro` に置き換える。相対パスが解決されない場合は `--extensionDevelopmentPath` に該当ディレクトリの絶対パスを指定する。CLIフラグや開発Host自体をKiroが拒否した場合は操作を止め、その結果を返す。APIの有効化や製品ファイルを独自改変しない。

全操作は生成された `dist/` 内のfixtureで行い、ソース側のfixtureは編集しない。再試行時はHostを閉じ、prepareを再実行して未実行状態に戻す。カーネル選択はフォーム初期表示の観察が終わるまで不要。Pythonは標準のセル▶だけで実行する。

## ケースと合格条件

フォームが「見える」だけでなく、選択・入力可能であることを確認する。`inset-requested` は要求の記録、`inset-ready` はWebview内のJavaScript起動の記録にすぎず、どちらも配置・共存の合格証拠だけにはならない。

| ID | モード／操作 | 期待結果・判定条件 |
| --- | --- | --- |
| S1 | Stable Hostでコマンドパレット **Zizai Probe: Open Empty Notebook**。クリック・実行前に観察 | セル0=初期化、1=通常Python（識別metadataなし）、2=処理。全て実行番号なし・出力なし。Status Barの文字列は設定によって表示。選択欄・フォームは出ないのが対照実験の予測。要件①はこの経路では不合格 |
| S2 | **Zizai Probe: Open Seeded Output Control**。実行せずセル2を見る | 保存済みMIME output内だけにフォームが出る予測。表示場所がsource下のoutputであることを記録。これはPython未実行でも要件①の合格に使えない。描画されなければそのエラーも返す |
| S3 | S2のフォームを変更し、セル2の標準▶で実行。その後もう一度実行、標準の出力消去も試す | `probe output` と `5` が標準出力へ。保存済みフォームが消える／維持されない予測。UIを出力へ自動再注入していないことを確認。残った場合も実機の事実を記録し、常設成立は別に判定 |
| P0 | Proposed Hostで **Zizai Probe: Open Empty Notebook**。開いた直後、セルをフォーカスする前に画面を観察 | 要件①：セル2でsourceより上に選択欄＋入力欄が表示され、操作可能。出力なし・実行なし・カーネル未選択でも表示できること。フォーカスするまで出ない場合は常設条件の不合格として区別 |
| P1 | **Zizai Probe: Report Environment and Cells**。次に各コード欄を順にクリックしてもう一度報告 | `mode=insets`、対象IDE名・版、各cellのoutputTypesとexecutionOrderが空／null。visibleEditorsにセルのTextEditorがあるか、inset-readyが出るかを記録。セルエディターが露出しない・例外・CSPエラー・クリップは不合格の根拠 |
| P2 | セル1の選択欄を架空コネクタへ変え、値 `gate-001` を入力。通常Pythonに戻す。セル0も観察 | 要件④：通常Pythonは共通選択のみ、架空処理なら入力欄、初期化セル0は両方なし。セル2でも値入力可能。sourceは一切変わらず、選択・入力でPythonが実行されない |
| P3 | セル2へ `gate-002` を入力して、標準コード欄を手動編集（末尾の `2 + 3` を `2 + 4` に変更）。標準▶で実行 | 要件②③：同じセルでフォーム・編集可能な標準source・stdout `probe output`・結果 `6` が共存し、フォーム選択と `gate-002` が維持される。実行前／後の画面・報告を保存。API成功ログだけでは合格にしない |
| P4 | セル2に手動で `raise ValueError("gate-probe")` を追記し標準▶で実行。標準の出力消去も行う | Python例外が標準outputへ出て、フォームは選択・入力可能で値が維持される。出力消去後もフォームを維持。消える・重なる・再入力が必要なら不合格 |
| P5 | 別ファイルへ切り替え／復帰、縦スクロール、コード折りたたみ／展開を行う。必要ならセル数を増やして画面外へ出す | 補助制約：仮想化でWebviewが破棄・再生成されても別セルに値が混ざらず、復帰後に使えるか記録。通常保存・再オープンの永続化は本試作では対象外（値を破棄）。折りたたみ中まで常設可能かも制約として記録 |
| P6 | Notebookで失敗した場合に **Zizai Probe: Open Text Editor Control** | 通常 `.py` エディターでinsetが出るならNotebook固有の制約を切り分けられる。この成功でNotebookを合格にしない。両方失敗ならAPI許可・Webview起動・IDE差異をログで確認 |

要件⑤は、各IDEでP0〜P4が合格し、正確な対象版と証跡が揃った場合だけ合格。標準APIのみで成立したか、試験的API・起動フラグ付きでのみ成立したかを別記する。どちらかのIDEが未実施なら全体ゲートは未達。
