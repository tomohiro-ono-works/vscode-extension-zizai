# 開発手順

## 作業開始前

担当Issue・親Issueと関係する現行仕様・設計を確認し、ゴール、スコープ、制約、完了条件を作業の基準にします。Task を作成・分割する場合は [Task・Subtask の作成ルール](tasks/task-rules.md) に従い、ユーザーの依頼に基づいて領域、工程、開始条件、依存関係を記録します。[Task のひな形](../template/task.md) と [Subtask のひな形](../template/subtask.md) をIssue本文へコピーして利用できます。進捗・判断・結果はIssueで更新し、既存のTask Markdownには二重記録しません。

仕様変更が含まれる場合は、その Task や適用されるルールで必要とされる承認を確認してから正本の仕様へ反映します。未承認の提案と決定済みの内容を区別し、承認の事実を推測で記録しません。

## 作業の流れ

1. 関係する仕様・設計・コードを調査し、変更内容を設計する。
2. 必要な技術評価・承認を確認する。
3. 変更に応じたテストケース・手動確認項目を作成または更新する。
4. Task の範囲内で実装し、再現可能なテスト手順を整える。
5. 必要なテストを実行する。
6. 結果を記録し、失敗を修正して関係する確認を再実行する。
7. 完了条件、未実行の確認、残作業を確認してIssueを更新し、完了条件を満たした場合にCloseする。

文書や配置のみの変更では、リンク、配置、差分など変更に合う確認を行います。実行していないテストを成功扱いにしません。

## テスト計画・実行時のルール

### テストの分類と担当

分類は、スクリプトをCLIから起動したかではなく、実際の操作・検証経路で決めます。Taskの工程区分とは分けて扱います。

| 種類 | 確認する内容・操作経路 | 基本担当 |
| --- | --- | --- |
| 単体テスト | 関数・個別処理の入力と出力、エラー処理 | エージェント |
| API・結合テスト | API・コマンド経由の処理、連携、データ・イベント・保存結果 | エージェント |
| UI自動テスト | 画面上の要素に対するクリック・キー入力と、表示・画面状態の検証 | エージェントがスクリプトを作成・保守。開始方法と担当は事前に合意 |
| ユーザーテスト（手動UI） | ユーザーによる実操作、表示、フォーカス、ショートカット、操作感 | ユーザーが操作・簡単な報告。エージェントが準備・証跡採取・分析・記録 |

- 実機で動かしたAPI・コマンド経由のテストも、手動UI検証とは別に記録する。同じ内部処理を呼び出せても、UIの入力経路・前提条件が同一とは限らない。
- API・結合テストやUI自動テストの成功を、指定された手動UI検証の合格へ振り替えない。ユーザーの操作対象をエージェントの判断で自動操作へ置き換えない。
- UI自動テストではPlaywrightを採用する。対応できない場合は、別方式へ切り替える前にユーザーへ相談する。
- UIの入力経路を確認する場合は、Playwrightのクリック・キー入力等を使う。内部関数・状態の直接変更や、ページ内JavaScriptによる直接のイベント発火を、同じ入力経路の証拠にしない。代替・モックを使った箇所は記録する。
- ユーザーが自動テストの開始を担当しても、操作自体が自動ならUI自動テストとして扱う。誰が開始するかと、操作が手動か自動かを混同しない。

### 計画と実施結果

- ケースごとに、目的、分類、操作経路、期待結果、担当、対象版・環境、開始条件、取得する証跡を定める。自動化する対象・範囲は実装前に明確にする。
- 手順・スクリプト・設定が実在し、準備が成功したことを確認してから実行を案内する。CLI終了コードや起動ログだけで、対象ケースの実行・成功を判定しない。
- API経由・UI自動・手動UIの結果を区別し、合格・不合格・未実施・対象外と観測限界を記録する。条件を変えた再確認は過去結果を上書きしない。
- 既存スクリプトと必要箇所のログを優先する。GUIの不明な状態に対して、理由のない再起動・再試行や大量ログの再読込を繰り返さない。切り分けできない場合は、確認済みの事実と不足情報を提示する。

## クラウドでの開発

- 既存のクラウドチェックアウトで作業する。クラウドタスクは隔離済みのため、ユーザーから指定されない限り追加の Git worktree を作らない。
- ソース編集、依存関係の導入、ビルド、自動テストを行う。現在は製品ソースと製品ビルドが未実装のため、そのコマンドは実装Taskで整備する。既存試作の入口と実環境の版は[環境・配布経路の検討案](research/development/TASK-006-01.md)を参照する。
- デスクトップで試す変更は、対象ブランチ・コミットを明確にして GitHub 経由で受け渡す。クラウドとローカルのファイルが自動同期されるとは想定しない。

## デスクトップでのユーザーテスト

- エージェントがテスト対象のブランチ・コミットをローカルで取得し、その版に対応する依存関係・拡張・設定・架空データ・ログ採取を準備し、ビルドと実行可能な事前確認を済ませる。
- ユーザーは検証対象のUI操作と表示・操作感の簡単な報告を担当する。ターミナル操作、設定ファイル編集、ログの手作業での整理を依頼しない。エージェントが保存ファイルの収集・比較・分析・結果記録を担当する。
- 環境準備としてのアプリ起動・終了は、検証対象のUI操作と区別する。方法・担当、専用ウィンドウの見分け方、終了時の整理方法を事前に決める。自動起動が技術的に可能なことを、実環境で安定して利用できることと同一視しない。
- 準備完了を報告し、ユーザーの開始合図を受けてから起動・実行する。別作業中のユーザーへ予告なく操作を求めたり、待機期限で案内中のウィンドウを自動終了したりしない。
- 診断ウィンドウは必要数に絞り、未保存変更を保護して合意した方法で整理する。通常作業用や他Taskのウィンドウを起動・終了の対象に含めない。
- 一度に小さな操作単位で、確認内容、対象ウィンドウ、実在するコマンド・ボタン名、番号付き手順、期待表示、報告例を案内する。報告後にエージェントがログを確認してから次を案内する。
- 問題発生時は収集済みログを先に確認する。再操作が必要な場合は、理由・許可範囲で行った修正・前回と異なる確認点を説明する。
- 製品の起動設定を実装した後、VS CodeのExtension Development HostとJupyterのPythonカーネルで確認する。製品用デバッグ・VSIX作成は未整備。既存の.vscode/launch.jsonは試作・診断用であり、[セル下部UI](../tests/manual/TASK-001-01-statusbar.md)と[NodeForm評価](../tests/manual/TASK-001-02-nodeform.md)のF5手順がある。
- Notebook UI、セル source / metadata、標準のセル実行、保存・再オープンを、Task の完了条件に応じて確認する。
- Windows 固有の操作や外部サービスを使うコネクタは、必要な OS・権限・接続先を用意したデスクトップで確認する。
- 手順と期待結果は `tests/manual/`、実施結果は担当Issueに記録する。クラウドでの確認とデスクトップでの確認を区別する。

## 設定・データの扱い

- 認証情報や個人情報をソース、共有設定、Notebook、テスト結果へ直接保存しない。クラウドとデスクトップそれぞれで必要な認証を用意する。
- ローカル設定は `config/`、ログは `logs/`、実行結果は `results/` に置く。共有するのは秘密情報を含まない設定例や手順に限る。
- Notebook は出力や metadata も保存する。コミット前に、実データ・認証情報・個人情報が含まれていないか確認する。
