## 依存解決とライフサイクル

- 依存の導入先は、Notebookで選択したカーネルのPythonと一致する必要がある。VS Codeのターミナルのpythonやpipが同じ環境とは推測しない。実機ではsys.executable・版・import先を記録して照合する。
- sys.path／PYTHONPATHへライブラリを見せることと、その依存を導入することは別。I7ではライブラリ自体の場所を指定しても、欠落した依存のModuleNotFoundErrorが通常どおり発生した。
- 同名モジュールはsys.modulesに残る。I5では探索パスの先頭をAからBへ変えても、再importでAの同じオブジェクトが返った。I6の新規PythonプロセスではBを読み込めた。これは通常プロセスの確認で、Jupyterカーネル再起動を実行した結果ではない。
- sys.pathの変更、Python変数・インスタンス・読み込み済みモジュールはプロセス内の状態。カーネルを再起動した後の初期化セルの再実行や、起動環境からの復元を既存カーネルで確認する必要がある。独自のモジュール再読込・カーネル管理・変数同期は追加しない。
- Notebookのクローズとカーネル停止は同じ操作とは限らない。複数Notebookが同じ／別カーネルを使う場合の変数共有はJupyter標準に従い、HostのNotebook別状態と混同しない。今回は共有・分離を実証していない。
- ライブラリと拡張機能の個別版管理、初回は独自の互換性チェックを実装しない方針は維持する。Python版・OS・ネイティブ依存の適合、実際のZIPの導入は後続で確認する。

8件すべて期待結果に一致し、probe全体は終了0。I1・I4・I7・I8の子プロセス終了1は、期待した欠落／例外が通常どおり現れることを確認した結果。プローブ側でPythonの例外を製品用通知へ変換する仕組みは作っていない。パッケージ導入・既存環境の永続変更はなし。一時フォルダーは終了時に削除した。

この結果は通常Pythonの探索・キャッシュ・例外の根拠であり、標準Notebookでの表示、例外出力、既存カーネルでの依存解決、実際の生成コードや配布物の合格には数えない。
