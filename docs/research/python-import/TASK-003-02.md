## 利用者から受け取った設計条件

このチャットで以下の回答を受け、その反映後の本書に「OKです。つぎに進んでください。」との了承を受けた。了承は本書の設計方針を対象とし、未確定の依存版・個別APIや他領域の契約案全体へ広げない。

- Pythonコネクタの用途について「フォームにPythonコードを入力して実行する」「通常のPythonセルでよい」。Pythonは通常セルとして扱い、専用Pythonコネクタ・フォーム・実行APIを設けない設計とする。
- 未設定時について「うまく設定しなかったらpythonが生成されない」「実行されたらPythonのコードが実行されるのでデフォルトの機能で問題ない」。設定成立時に処理コードを生成し、実行はセルsourceをJupyter標準機能で評価する。未設定用の例外コード・独自の実行可否判定・Run All制御を追加しない。

その結果、構成は通常Pythonと専用6コネクタ（CSV、Excel、DuckDB、BigQuery、Data Integration、Shell）として整理する。既存仕様の「初回7コネクタ」とP01の未決記載には整合反映が必要である。本書は変更理由と受け渡しを記載し、現行仕様や他Issueを更新済みとは扱わない。残るアクションの採否まで決定した意味ではない。

## ソースとimportの対応

次の配置を後続へ渡す。具体的な製品ファイルの作成範囲と収集設定は、適用ルール・契約の対象部分を確認してから固定する。

| import先 | 正本ソースの配置案 | 責務 |
| --- | --- | --- |
| `zizai` | `apps/core/src/zizai/` | 最小限のパッケージ入口 |
| `zizai.core` | `apps/core/src/zizai/core/` | 複数コネクタに実際に必要な共通処理 |
| `zizai.connectors` | `apps/connectors/src/zizai/connectors/` | 個別コネクタのパッケージ |
| `zizai.connectors.csv`等 | 上記connectors配下のモジュール | 形式・サービスごとのアクション |

rootの配布設定でpackageとディレクトリの対応を明示し、1つのwheel内の`zizai/`へ収集する。親packageの`__init__.py`はcore側だけが所有し、connectors側に同じ親の初期化ファイルを重複させない。収集後のコピーは生成物とし、正本として編集しない。開発確認も収集した配布物からのimportを基本にし、Notebookへ開発用sys.path設定を要求しない。具体的なsetuptools設定とwheel内容はTASK-006-02で検証する。

契約の正本・言語別表現・生成／同期・陳腐化検出はTASK-005-04が定義する。Python側へ必要な資産だけを収録し、導入後にリポジトリの`apps/common/`を参照しない。実行時に必要な資産はpackage内から取得できる収録方式を照合する。Host・UIのソースや不要な開発資産はwheelへ含めない。

## 責務・依存方向・ライフサイクル

- コネクタから共通基盤を利用する。共通基盤から個別コネクタをimportせず、`import zizai`も全コネクタや全SDKを一括importしない。
- 共通処理は、複数コネクタに必要な入力検証・変換等に限定する。CSV、Excel、SQL、認証、BATや個別の副作用はコネクタが所有する。空の汎用Engineや一律の基底クラスを先に作らない。
- 初期化セルは対象コネクタのimportとインスタンス生成を行う。初期化だけで入力ファイルの読取・認証・通信・SQL・BATを実行しない。ファイルは処理セル実行ごとに読む。
- インスタンスと表はカーネルに保持する。グローバルな業務context、Node.jsへのDataFrame同期、子PythonでのJSON往復を導入しない。
- 戻り値はPythonオブジェクトとして返し、入力不正・依存欠落・個別処理の失敗は通常のPython例外として伝播させる。一律の成功辞書・文字列に変換しない。
- 更新後は標準カーネル再起動と初期化セルの再実行を基本にする。独自のreload・自動pip・venv／kernelspec作成・起動時互換性チェックは設けない。

## 最小依存と手動導入

表の共通型は`pandas.DataFrame`を推奨候補とし、TASK-004-02／TASK-005-03で正式に照合する。共通基盤の入口に不要な重いimportを置かず、採用する処理から必要な依存を追跡する。

| 直接依存の候補 | 必要性を確定する条件 |
| --- | --- |
| pandas | DataFrameを扱う採用処理 |
| openpyxl | 採用するxlsx系Excel操作 |
| duckdb | DuckDB操作 |
| google-cloud-bigquery | BigQuery操作 |
| google-auth | 自作コードから認証APIを直接利用する場合。SDK経由の推移依存とは区別する |
| numpy | 自作コードが直接利用する場合のみ直接依存にする。旧基盤が使っていたことを根拠にしない |

全採用アクションに必要な集合をwheelの依存宣言へ記録する。Python通常セルとShellの結果を表に統一するためだけの依存は追加しない。PyArrow・db-dtypes・BigQuery Storage関連、`pandas[all]`や旧アプリ全依存は一律採用せず、採用APIに対応付ける。gcloudや別Python本体の追加導入を必須にしない。BigQueryの初回認証経路はTASK-004から入力が必要である。

PR #49の比較入力6件・推移依存込み30件のwheel解決は製品の依存宣言やlockではない。許容する依存範囲と、再現用に固定した対象OS／Pythonの集合は分けて管理する。Windows11 x64・通常ABIのCPython 3.14.3は検証基準候補であり、最低版や`Requires-Python`、全依存の実import適合は未確定。

VSIXと自作wheelをZIPへ同梱し、wheelは選択カーネルと同じPython環境へ手動導入する。実際の導入コマンドは実配布物・依存固定・対象環境が揃ってから定義する。通常の生成コードにはZIP展開先やsys.path操作を埋め込まない。利用者へNode.js・npm・ビルドツールを要求せず、第三者wheelの全同梱・完全オフライン導入も新要件にしない。任意展開先からの実導入・importは未確認である。

## コード生成と標準実行の境界

| 状況 | sourceの扱い |
| --- | --- |
| 新規アクションが未設定／入力不正 | 有効な処理コードを生成しない。未設定を示すためのraiseも生成しない |
| 同じアクションの設定を編集中 | 既存方針どおり下書きを保持し、確定済みsourceは維持する |
| 確定時の検証NG | 新しい処理コードを生成・反映しない。確定済み設定とsourceは維持する |
| 確定時の検証OK | 有効な設定からHostがsourceを生成・反映する。生成だけでは実行しない |
| コネクタ／アクション切替 | 旧設定を破棄し、旧アクションのsourceを新アクションのコードとして残さない。新設定が未成立なら処理コードを生成しない |
| 標準実行 | その時点のセルsourceをJupyterが実行する。実行禁止・独自の成功判定を追加しない |

「生成しない」は不正な新設定のコードを作らないという条件であり、既存の下書き編集で確定済みsourceを削除する指示には広げない。未設定状態の具体的なsource更新、切替時の原子性、初期化セルとmetadataの整合はTASK-005-02／03とTASK-002-02で照合する。先行案のU1（未設定用ValueError）は採用せず、U2の説明コメントを必須にも扱わない。フォームで見える値だけではファイルの存在・認証・実変数の型までは保証できず、生成済みPythonの実行時エラーは標準の例外表示に従う。
