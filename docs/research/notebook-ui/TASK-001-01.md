## 目的・実施範囲

通常のJupyter `.ipynb` コードセルへ、Python実行前から選択欄・簡単なフォームを常設し、標準source・標準outputとの共存と実行後の維持ができるか調べる。実行前・outputなしの初期表示を必須とし、保存済み／Python実行後のoutput内にフォームが出ただけでは合格にしない。

利用者はTASK-001-01の検証用コード・起動設定・手順を許可している。`apps/`、コネクタ、正式な共通契約、独自カーネル・実行サーバー・Run All・DataFrame同期、他Subtaskには着手しない。side panel等への方針変更も確定しない。

作業基準は `chore/project-structure` の `56e325c71a6f02b900f38ab28160a5dc9955814a`（Task整理）、作業ブランチは `spike/task-001-01-notebook-ui`。初回はfetch設定がmain限定でブランチが見えず、通常sandboxのプロキシ接続も失敗した。ネットワーク権限付きで `git ls-remote --heads origin` を確認し、当該refを明示fetchして取得した。Taskを再作成せず既存Taskから開始した。

## 最小検証計画と判定

1. 固定版の標準API・提案APIと実装を照合する。Renderer、Status Bar、decorations、Webview、editorInsetsを切り分ける。
2. 標準APIのみの対照用extensionを準備。出力ゼロのNotebookと、保存済みMIME outputだけを持つNotebookを比較する。
3. 別モードで `editorInsets` を有効化し、見えているNotebookセルのTextEditorにフォームを挿入できるか試す。対象は同じfixture。outputを挿入・再注入せず、既存Jupyter実行に委ねる。
4. VS Code／Kiroの各実機で、初回表示・入力・通常Python／初期化セル・標準実行前後を観察し、版・画面・ログを保存する。

合格には、処理セルの選択欄＋フォームがsourceより上に出て、出力なし・実行なしで操作でき、標準source編集・output表示と共存し、実行とoutput消去で選択・入力値を失わないことが必要。通常Pythonでは共通選択だけ、初期化では両方非表示。両IDEの結果を別々に揃える。API呼び出し成功、Webview ready、構文チェックだけでは合格にしない。

## APIの調査結果

一次根拠はVS Code **1.142.0**、commit **`d956e8a6ac5d904486557eea07e1d6bd62a4d36f`** のソース／型定義。調査時のmainは1.143.0で可変なので、判定根拠には用いない。実機の「最新」が異なる場合はその版へ再照合する。

| 仕組み | 区分／できること | 本要件に対する制約 |
| --- | --- | --- |
| Notebook Renderer (`contributes.notebookRenderer`) | 標準。特定MIMEのセルoutputをHTML/JSで描画 | 空のコードセルにフォームの独立スロットを作るAPIではない。保存済みoutputを表示すればPython実行前にも見えるが、source上のUI常設や実行後維持を保証しない |
| NotebookCellStatusBarItem | 標準。source下のStatus Barに文字列・tooltip・Command | HTML/select/inputは受け付けない。クリックからQuickPick等を開く案は別UI方針であり要件と同じではない |
| TextEditor decorations / CodeLens | 標準。装飾・文字列・コマンド | 任意のHTML入力フォームの配置口ではない |
| WebviewPanel / WebviewView / CustomEditor | 標準。HTML UIを提供できる | 別タブ／View、または既存Notebookを置き換える独自editor。通常Jupyterセル内の所定位置へ常設するものではない。今回は作らない |
| NotebookEdit / NotebookCellData.outputs | 標準。セル内容・metadata等の編集、セル生成時のoutput指定 | UI専用領域を追加するAPIではない。output付きセルの挿入・置換を表示維持策として採用しない |
| `window.createWebviewTextEditorInset` (`editorInsets`) | **試験的**。TextEditorの行間にWebviewを置く | Notebook専用APIではない。セルのTextEditor取得、行高・Notebook高さ、複数セル、仮想化・破棄、実行後維持は未実機確認。可能性が残るが採用不可／可を確定できない |
| notebookMessaging / contribNotebookStaticPreloads | **試験的**。renderer側のpreload・通信に関係 | preloadingと入力セルUIの配置は別。controller側の責務やoutput/markup領域に関わる。新controllerを作る方策は今回の制約外で試作しない |

## 最小試作と依存・設定

- ソースは [tests/notebook-ui-gate](../../../tests/notebook-ui-gate/)。依存npmパッケージ0、JSをそのまま実行するためコンパイルなし。prepareはファイルコピーとモード別manifest生成のみ。package-lockは不要。
- `stable` manifestに `enabledApiProposals` はなく、対照用Status BarとRendererのみ。`insets` manifestにだけ `editorInsets` を付与。VS Code API最低宣言は `^1.105.0`（Jupyter基準版との整合用）で、全ての1.105以上でUI成立したという意味ではない。
- [.vscode/launch.json](../../../.vscode/launch.json) と [tasks.json](../../../.vscode/tasks.json) がF5用の準備・起動入口。両モードの拡張IDは `zizai-lab.task-001-01-probe`、試作版0.0.1。
- fixtureは通常のPythonコードセル3個（初期化／metadataなし通常Python／処理）。`empty.ipynb` はoutputゼロ・execution_count=null。`renderer-control.ipynb` は処理セルに架空MIMEの保存済みoutputだけを持ち、Python実行後にUIを生成するコードは含まない。
- UIは架空コネクタ選択＋1入力のみ。コード生成・確定・保存・本物のコネクタ処理はなく、正式metadata schemaや層間契約は作らない。初期化の識別はfixture専用の印で、生成・重複検知は実装しない。
- insetの値はHost一時メモリに保持。実行でUIが消えることを隠すoutput再注入や実行後再描画はしない。画面復帰時の通常ライフサイクルによる再生成は、表示が継続したことと分けてログで観察する。
- Webviewはローカルmoduleのみ、CSP付き。実データ入力・ネットワークアクセス・OS連携なし。ログにsource・入力値は保存しない。認証情報や外部サービスは不要。

## 結論・後続への影響

次に必要なのは手動手順S1〜S3／P0〜P6の両IDE結果、IDE・拡張・カーネルの正確な版、画面とログ。成立した場合も試験的API許可・配布制約、仮想化、折りたたみ、高さ固定、複数セル、実行後維持を明記し、正式設計で採用可否を判断する。

成立を前提とするTASK-001-03／04および関連Host設計は開始条件未達。TASK-001-02、TASK-002以降の調査・設計・実装を今回の結果で開始しない。正式なUI／Host契約やmetadataを先に固定しない。

不成立の場合の再協議案（未採用）：

- Status Bar／セルtoolbarからQuickPickとWebviewView等を開く：標準API中心だが「同じセルに常設」を変更する必要がある。
- output内フォーム：標準Notebookの表示口を利用できるが、outputなしの初回表示・実行での置換・source上の配置要件に合わず、現条件では採用できない。
- Notebookのフォーム用slotをIDEの拡張APIとして追加する／上流へ要望する：既存Notebookを保てる可能性はあるが、IDE変更・保守・両IDE対応が別課題。
- 独自CustomEditor等：標準Notebook体験を置き換えるため、目的・制約の見直しが必要。今回実装しない。

いずれもUI方針を勝手に変更せず、実機結果と影響を揃えて利用者へ返す。
