## 2. 方式の比較と推奨

| 案 | 利点 | 制約・判断 |
| --- | --- | --- |
| A：Hostが正本を持ち、要求／応答＋全体snapshotを送る（推奨） | metadata更新後の状態をUIが復元でき、要求の対象・版を検証できる | 小さなフォーム単位の全体値を送る。全体snapshotをUIの未送信入力へ無条件適用しない規則が必要 |
| B：UIが状態を持ち、項目ごとの差分を送る | 通信量を減らせる | 再表示・切替・失敗時の差分回復が増える。初回は採らない |
| C：セル番号・Notebook URIだけで操作する | 形式が小さい | 移動・同名／再オープン・遅延応答を区別できないため採らない |

UI設計の概念名や評価用メッセージを流用せず、以下の候補を005-04でschemaへ落とす。JSONのみを境界に使い、Pythonオブジェクト・source・任意のOS命令をメッセージへ含めない。

## 3. 識別と一時状態

| 候補キー | 発行・寿命・用途 |
| --- | --- |
| `viewSessionId` | HostがWebview生成／再接続時に発行。旧Webviewからの要求と応答を無効化する |
| `notebookSessionId` | 編集用NotebookタブとNotebookDocumentの対応へHostが発行する論理セッション。URIとは別。最後の編集用タブ終了またはdocument.closeで失効。同じAPIオブジェクト／同じpathの再表示でも失効済みなら再発行。Save AsでDocumentが入れ替わっても失効 |
| `cellId` | 管理開始時にHostが発行する32桁小文字hex UUID。metadata保存用。コピーされ得るため、単独で適用先を決めない |
| `cellSessionId` | 現在所属するNotebookCellの生存参照へHostが発行。移動で同一性が確認できれば保持。実削除・再生成・Undoで参照が変われば再発行 |
| `targetGeneration` | サイドバーの対象変更・再選択・アクション変更・無効化時にHostが増加。表示対象の世代。通常の下書き更新では増やさない |
| `actionGeneration` | セルのアクション／mode変更時、所有metadataの外部変更／Undo時にHostが更新する不透明token。A→B→Aでも再利用しない |
| `stateRevision` | セルの観測状態ごとにHostが増やす整数。下書き・source・所有metadata（zizai）・役割の変更で増加。外部変更やUndoでも過去値へ戻さない。永続化しない |
| `requestId` | UIがviewSession内で一意に発行。Hostは処理中と処理済みの応答をキャッシュする |
| `editSequence` | UIが対象世代ごとに増やす入力番号。未送信／未確認入力とsnapshotを区別する |

`TargetRef` は `notebookSessionId`・`cellSessionId`・`cellId`・`targetGeneration`・`actionGeneration` の組。UIのURI・表示セル番号・connector名からHostが参照を再構築しない。Host発行の組を生存参照・所属・役割と照合する。通常Pythonのセル選択UIからの操作も、Hostが当該セルの生存参照へ結び付ける。サイドバーを経ない選択操作では、Host内部で同等の版検証を行う。

NotebookDocumentが残っていても最後の編集用Notebookタブが閉じた時点で、この契約の「Notebookを閉じた」に対応させる案。公開Tab APIとNotebook APIをHostが照合し、タブ一覧の変化とdocument.closeの両方で論理セッションを管理する。同じNotebookを複数の編集用タブで開いている場合は最後の1枚まで保持する。サイドバー非表示・フォーカス移動・別Notebookへの一時移動だけでは論理セッションを破棄しない。

終了時にtarget、保留path選択、切替transition、元source一時退避を失効させる。標準編集APIへ既に渡した編集や、カーネルへ送信された処理を取り消したことにはしない。再表示時には「設定」で新targetを選び直し、旧要求を同じAPIオブジェクトへ適用しない。Tab APIで対象を一意に対応付けられなければフォーム操作を停止する。複数タブ・Save As・タブ終了直後の要求競合はD5の製品適合条件として残す。

移動は構造変更イベントの処理後に現在の所属を調べ、remove/addの片側だけで削除と断定しない。実削除・クローズ・対象不明では要求を失効し、隣のindexへ付け替えない。永続ID重複時は双方のフォーム変更を止め、sourceから元セルを推測しない。新しいIDの付与・初期化セルの重複解消は002-02との設計確認事項とする。

複製・貼付でmetadataが消える経路は通常Pythonとして扱い、元の設定・一時退避・実行状態を推測復元しない。sourceは標準操作が複製したまま残る。フォーム編集は利用者が処理を選び直して開始する案であり、標準の複製sourceから設定も自動復元する仕様は追加しない。

## 4. 通信形式案

### 4.1 共通envelope

要求は `protocolVersion: 1`、`kind: "request"`、`requestId`、`viewSessionId`、`method`、`payload` を必須とする。セル変更操作には `target: TargetRef` と `expectedRevision` を追加する。読取のstate.readは表のとおりexpectedRevisionを持たない。対象選択はURI指定の要求にせず、Hostの「設定」コマンドが対象を決めてsnapshotを配信する。

応答は `protocolVersion: 1`、同じ `requestId`・`viewSessionId`・対象の組と、`kind: "response"`、`status: "ok" | "invalid" | "conflict" | "cancelled" | "error"` を返す。成功応答には確定した `stateRevision` と要求に応じた結果を返す。invalid／conflict／errorには `error: {code, messageKey, fieldErrors?}` を返し、cancelledにはerrorを付けない。`messageKey` は定義済み表示文のキー、`fieldErrors` は `{fieldId, code, messageKey}` の配列。入力値や例外stackを表示文へ埋め込まない。

イベントは `kind: "event"`、`protocolVersion`、`viewSessionId`、`event: "state.snapshot" | "target.prepareChange" | "target.changeAborted" | "target.invalidated"`、Host単調増加の `eventSequence` と `payload` を持つ。snapshotは対象、版、表示用Notebook名・現在位置、mode、選択、フォーム、下書き、確定値、`acceptedEditSequence`、状態を含む。新しい対象世代では入力番号0から始める。初期状態は `target: null`。無効化理由は `deleted | notebookClosed | differentNotebook | ambiguous | unsupportedMetadata`。単なるサイドバーフォーカス移動は `differentNotebook` にしない。

```json
{
  "protocolVersion": 1,
  "kind": "request",
  "viewSessionId": "view-example",
  "requestId": "req-example-7",
  "method": "draft.replace",
  "target": {
    "notebookSessionId": "notebook-example",
    "cellSessionId": "cell-example",
    "cellId": "00000000000040008000000000000001",
    "targetGeneration": 3,
    "actionGeneration": "action-example-2"
  },
  "expectedRevision": 12,
  "payload": {
    "editSequence": 7,
    "definitionVersion": 1,
    "values": {"file_path": {"kind": "text", "text": "data/new.csv"}}
  }
}
```

### 4.2 要求一覧

| `method`候補 | `payload` | Hostの効果／応答 |
| --- | --- | --- |
| `view.ready` | 空object。target・expectedRevisionなし | 登録したviewへ最新snapshotと選択候補を再送。製品版のPythonとの互換性確認ではない |
| `state.read` | 空object。target必須、expectedRevisionなし | 現在対象を再読する読取要求。値が変わっていれば新revisionのsnapshotを返す。下書き／source／metadataを書き換えず、未確認入力を上書きしない |
| `selection.change` | `selection: {mode:"python"}` または `{mode:"action",connectorId,actionId}` | 定義に存在する選択のみ受付。新しい初期値・未設定source・初期化セルを計画し、旧値を破棄。UIだけを先に成功状態へしない |
| `draft.replace` | `editSequence, definitionVersion, values: DraftValues` | 全体下書きをmetadataへ。項目値の途中不正は保持可能。構造不正・未知項目は拒否。source不変。`acceptedEditSequence` を返す |
| `params.commit` | `editSequence, definitionVersion` | 当該番号まで保存確認済みの下書きをHostが検証・正規化。確定値・sourceを更新。異なる番号や未確認下書きならconflict |
| `target.flush` | `transitionId, editSequence` | target.prepareChangeへの応答要求。旧対象の最後の入力までmetadata反映済みか確認し、Hostが保持する次対象への切替を許可する |
| `path.pick` | `fieldId, fieldEditSequence` | 定義が許すfile／directory選択のみ。条件は登録済み定義から取得し、UIが任意コマンド・ダイアログ条件を指定しない |

`path.pick` の成功値は `{fieldId, fieldEditSequence, path}`。同じ対象・アクション・要求・項目の編集番号がまだ有効な場合だけUIへ反映し、通常の下書き更新を送る。ユーザーがその欄を編集した後の選択結果は採らない。キャンセルは `cancelled`、値・下書き・sourceを変えない。Host側のURI→kernel pathが保証できないRemote／WSL等では `PATH_MAPPING_UNAVAILABLE` とし、自動変換を推測しない。初回のローカルWindows候補との対応は実機確認を要する。

### 4.3 順序・再送・対象切替

UIはセル変更要求を1件ずつ送る。入力は1編集ごとに順序を保持してキューへ積み、直前の成功版を次のexpectedRevisionへ使う。初回案ではdebounceや入力の間引きを追加しない。性能・UndoのD6で成立しなければ方式変更を別途判断する。

snapshot／応答を受けても、その `acceptedEditSequence` より新しいローカル入力を上書きしない。フォーム値の復元・setParamsは入力イベントの再送を抑止する。Host状態とUI未確認入力の差がある間は「保存済み」と表示せず、確定・対象切替前にキューを完了させる。

別セルBの「設定」はHostに切替予定を保持し、`target.prepareChange` を `{transitionId, target: 旧対象A}` とともに送る。UIはAの入力を一時停止してキューを完了し、最新expectedRevisionと最後のeditSequenceを持つ `target.flush` を送る。Hostが番号一致・対象生存を確認して初めて新targetGenerationを発行し、Bのsnapshotを送る。transitionIdの失効・応答不能・下書き保存失敗ならAと入力を維持して切替を止める。切替待ちにさらに別の「設定」が来た場合も要求順に直列化し、旧transitionIdを再利用しない。これは拡張内の操作順序であり、標準セル実行や手動source編集は制限しない。サイドバー消滅時の未送信値は永続化を保証できず、再接続ではHost確認済みmetadataから復元する。

未編集の初期フォームはeditSequence=0で確定でき、Hostは定義の初期値を検証する。draftがnullかつcommittedがある場合はその値を使う。初期値・確定値のUI表示を下書き保存のためだけに再送させない。同じmode／connector／actionの再選択はno-opとし、再送以外でも値を破棄しない。

同じセルのアクション変更では旧下書きを破棄する既存規則を適用する。処理中のHost編集を終えてから、未送信の旧入力を捨て、旧path選択等を失効してselection.changeを処理する。表示対象の変更時の保持と混同しない。

HostはNotebookごとの拡張内編集を直列化し、適用直前に生存参照・現在index・source版・最新metadata・expectedRevisionを再確認する。同じrequestId／同じ内容の再送は同じ応答を返す。別内容は `REQUEST_ID_REUSED`。view再接続・Host再起動後は古い要求を受理せず、新snapshotから再確認する。タイムアウトで更新失敗と断定したり、新IDで同じ確定を自動再送したりしない。

dedup判定はrevision検証より先に行う。同じ要求の処理中再送はその処理へ合流し、完了後は当時の応答を返すため、古い応答を最新snapshotとして表示しない。キャッシュを破棄するときはそのviewSessionも失効させ、過去のrequestIdを未処理として再受付しない。revisionはNotebook.versionの写しではなく、所有するmetadata値・source・役割の観測変化へ付ける。実行要約だけのtransient変更ではstateRevisionを増やさず、必要な表示イベントだけを更新する。同値のdraft.replaceは値を比較し、metadata編集をせずにeditSequenceの確認応答を返す。入力値が変わった通知を間引く規則ではない。

transition開始後の下書き失敗・次対象喪失・revision競合は `target.changeAborted` を `{transitionId, code}` とともに配信する。旧対象が生存していればAの入力を再開し、Bへ進まない。旧対象も失われていればinvalidatedを配信する。失敗したtransitionIdのtarget.flushを後から受理しない。タイムアウト値はHost設計の運用値として別途定め、経過時間だけで保存成功を補完しない。

### 4.4 保存応答とsnapshotの具体例

前掲draft.replaceの成功応答例。モデル反映とディスク保存を分ける。error応答・snapshotも同じenvelopeの必須項目を満たす。

```json
{
  "protocolVersion": 1,
  "kind": "response",
  "viewSessionId": "view-example",
  "requestId": "req-example-7",
  "target": {
    "notebookSessionId": "notebook-example",
    "cellSessionId": "cell-example",
    "cellId": "00000000000040008000000000000001",
    "targetGeneration": 3,
    "actionGeneration": "action-example-2"
  },
  "status": "ok",
  "stateRevision": 13,
  "result": {"acceptedEditSequence": 7, "persistence": "notebookModel"}
}
```

snapshot.payloadの候補必須フィールドを次に固定する案。targetなし／喪失時はtargetにnullを置き、フォーム関連欄はnull、番号は0とする。表示位置は1始まりであり、識別には使用しない。

| 欄 | 型・意味 |
| --- | --- |
| `target, stateRevision, acceptedEditSequence` | TargetRefまたはnull、非負安全整数2つ。番号は同一viewSession／対象世代の中だけ比較 |
| `display` | `{notebookLabel, notebookHint, cellPosition}`。表示文string2つと整数またはnull。接続先の秘密情報を含めない |
| `mode, selection, definitionVersion` | modeはpython／action／initializationまたはnull。selectionはconnectorId／actionIdまたはnull、定義版は整数またはnull |
| `formDefinition` | 005-03のUI向け投影またはnull。Python module・method・keywordはUIへ配信しない |
| `committed, draft` | §5の保存値またはnull。表示時の値は005-03の復元規則で一意に構成 |
| `states` | §7のtargetState・draftState・applyState・sourceState・executionStateの5欄。localPendingはUIだけが重ねる |
| `capabilities` | `{canEditDraft, canCommit, canPickPath}` のboolean3つ。UIは必要な許可がfalseなら該当操作を送らない。Hostも独立に検証する |
| `notification` | nullまたは `{code,messageKey,fieldErrors}`。fieldErrorsは配列。Python例外・実データは含めない |

UIはviewSession不一致、失効targetの応答、古いeventSequenceを破棄する。同じtargetの遅い応答では、受付番号7への応答が到着しても8以降の編集中値を戻さない。表示に使うsnapshotと要求成否の履歴は別に扱う。

### 4.5 拒否と表示

| 条件 | status／code候補 | UIの扱い |
| --- | --- | --- |
| envelope不正・未知method／余分なキー | invalid／`INVALID_MESSAGE`・`UNKNOWN_METHOD` | 処理しない。IDを安全に抽出できない入力には応答せず破棄 |
| protocolVersion非対応 | invalid／`UNSUPPORTED_PROTOCOL` | フォーム編集を止め、同梱UIの再読込を案内。Python版との独自互換性チェックは作らない |
| 失効target・古い版・action変更 | conflict／`STALE_TARGET`・`REVISION_CONFLICT` | 値を別対象へ適用せず、最新snapshotとの確認へ。自動マージしない |
| 必須・型・範囲・変数名不正 | invalid／`VALIDATION_FAILED` | 項目下へ表示。下書き保持、確定値・source不変 |
| ファイル選択取消 | cancelled | 値を維持。エラー通知不要 |
| source生成失敗・Notebook更新失敗 | error／`GENERATION_FAILED`・`EDIT_FAILED` | 値を保持しフォーム上部に表示。サイドバー非表示ならVS Code標準通知で設定欄へ誘導 |
| 部分適用・競合で整合確認不能 | error／`INCONSISTENT_CELL` | 確定成功を表示せず対象のフォーム変更を止める。標準source・出力はそのまま閲覧可能 |

未知入力は業務呼出し／OS操作へ転送しない。JSONサイズ・深さ・文字列長の上限はフォームの最大入力（SQL等）と照合して005-04で数値化する受入条件とし、現時点で任意の閾値を製品制限へしない。CSP・許可資産・NodeForm許諾とpatchは001の設計を継承し、フォーム値・path・sourceを通常ログへ追加しない。

## 5. metadata案と復元

`.ipynb`上の保存場所は `cells[i].metadata.zizai` を候補とする。調査対象の内蔵ipynb adapterでは、API上は `cell.metadata.metadata.zizai`。外側と内側の所有外キーを、適用直前の最新値と併合して保持する。他serializerへの同一適用を前提にしない。

```json
{
  "zizai": {
    "schemaVersion": 1,
    "cellId": "00000000000040008000000000000001",
    "role": "action",
    "selection": {"connectorId": "csv", "actionId": "read_csv"},
    "definitionVersion": 1,
    "committed": {
      "values": {"file_path": {"kind": "literal", "value": "data/old.csv"}},
      "outputBinding": "zizai_result_00000000000040008000000000000001"
    },
    "draft": {
      "values": {"file_path": {"kind": "text", "text": "data/new.csv"}}
    }
  }
}
```

| フィールド | 規則候補 |
| --- | --- |
| `schemaVersion` | 整数1。文書schemaの版。拡張版・Python distribution版・definitionVersionとは別 |
| `cellId`・`role` | cellIdは必須。roleは `python \| initialization \| action` の判別子 |
| `python` | 追加のselection・draft・committedを持たない。未管理セルはmetadataなしでも通常Python |
| `initialization` | `connectorId` が必須。フォーム値なし。1コネクタ1セルの探索に使い、source文字列だけで同定しない |
| `action` | `selection`・`definitionVersion`・`committed`・`draft` が必須。選択直後のcommittedはnull。draftは未編集ならnull、編集時は全体値。空objectとnullを区別 |
| `committed` | 005-03のBoundValuesとoutputBinding。result=displayはHost発行名、result=noneはnull。最後の確定成功だけを記録。初期化・処理の実行成功を記録しない |
| `draft` | 005-03のDraftValues。途中の入力不正も保存。確定成功時、非表示の保持値がなければnullにする。保持値があれば、確定したactive値を含む全体DraftValuesを残して再表示に備える |

復元の優先順は `draft → committedをUI入力へ変換 → ActionDefinitionの初期値`。下書き／確定値の一方が不正なら、他方へ黙ってフォールバックして上書きしない。フォームの編集を止め、理由を示す。通常sourceと標準実行は維持する。

- zizaiなし：通常Python。sourceからフォームを推測しない。処理選択時に初めて管理metadataを作る。
- zizaiあり・版欠落、未知の版／role／connector／action／definitionVersion、既知版の未知キー・構造不正：読取保護状態。元metadata・sourceを変更しない。
- 正式v1以前のUI設計の概念JSON・試作キーは、公開済みの旧schemaとして自動移行しない。005-04で実際に配布済み形式を棚卸しして移行元を明記する。
- 版の移行は旧版→新版の専用変換・値保持・失敗ケースを定義してから行う。未知の将来版を現在版へ書き戻さない。初回案で暗黙の破壊的移行を追加しない。
- 再オープンは新しいNotebook／セルsessionとstateRevisionで始める。保存された下書き・確定値のみ復元。旧要求・target・元コード一時退避・実行状態は復元しない。

`viewSessionId`、session類、要求番号、入力番号、実行要約、未更新、元コード退避、DataFrame、認証情報はmetadataへ保存しない。通常Python→処理選択で退避する元sourceは、NotebookSession＋生存セル参照に結び付ける。アクション変更で元sourceを上書きせず、通常Pythonへ戻すときだけ利用し、Notebookクローズ・セル実削除で破棄。Undoで新参照へ戻ったセルに古い退避を自動対応付けしない。

## 6. 確定・失敗・Undoの契約

1. Hostは保存確認済みの下書きと定義を検証し、BoundValues・source・必要な初期化セルの編集計画をメモリに作る。この時点ではNotebookを変更しない。
2. 生存参照・所属・全対象の現在版／metadataを再確認し、最新の所有外metadataを保持して標準編集APIへ渡す。初期化セル挿入／探索も同じNotebookの直列処理内に置く。
3. applyEditの戻り値だけで成功とせず、対象・metadata・source・初期化セルの事後状態を再読する。計画全体と一致して初めてokと新snapshotを返す。
4. 適用なしなら旧確定値・source・下書きを維持してEDIT_FAILED。部分適用／他編集との混在はINCONSISTENT_CELL。値保持と成功表示抑止は保証要件だが、API上の自動巻き戻し・原子性は保証しない。
5. 不整合時に古いsnapshotでNotebook全体を上書き修復しない。次の再読・再確定案を002-02へ渡し、D3で検証するまで「失敗しても常に旧source／metadataを維持」の製品成立を宣言しない。

再読で使う基準は、要求前の所有metadata／source、今回の計画、要求後の実観測の3つ。適用false／例外後でも実観測が計画全体と一致し、対象が生存して他の競合を検出しなかった場合はモデル反映済みと判定できる。APIの戻り値とモデル状態を区別するため `result.applyOutcome: "verifiedAfterFailure"` を返す候補とする。部分適用をこの値で成功へ変換しない。通常成功は `applyOutcome: "verified"`。

| 再読結果 | 次に許すこと | 自動では行わないこと |
| --- | --- | --- |
| metadataもsourceも要求前と一致 | failedのまま値を保持し、再読版に対する明示的な確定を再度可能にする | 古い要求の新requestIdでの自動再送 |
| 計画全体と一致 | 同じrequestIdにモデル反映済み応答を返す。sourceと設定の対応だけを確認 | ディスク保存成功・Python実行成功の補完 |
| metadataだけ新、sourceだけ新、初期化セルだけ追加、または他編集との混在 | inconsistentとして編集を止め、state.readで最新状態と理由を表示する | 以前のsourceやNotebook全体への自動巻き戻し |
| 最新metadataが既知版で整合し、対象・定義が一意。再生成内容と現在sourceの差だけが残る | 既存の「確定」を明示的に再度押して再生成する経路を提案。未送信入力を消さず、最新revisionに対し再検証する | 「再読」だけをsource修復や成功通知の契機にする |
| 未知／不正metadata、重複ID、初期化セル重複、所属不明 | read-onlyを維持。標準Undo／利用者の編集後に再読し、正常条件を再確認する | 誤ったセルの選択、推測移行、独自Undo |

再確定を再度有効にできるのはHostが最新状態を完全に検証できた場合だけで、その時点ではfailedとcanCommit=trueを配信する。検証できなければinconsistentとcanCommit=falseを維持する。競合前のUI入力が最新metadataと異なる場合は、両方を保持して競合を表示し、自動マージ／自動上書きは行わない。未送信入力を新revisionへ自動付け替えする方式も採らない。具体的な競合解決操作が必要な部分は001／002との共同設計に残す。

source変更とmetadata変更が途中で分かれる窓を契約だけで消すことはできない。PR #50の「Hostが整合を保証する」要件に対して、これは**未充足の実装ゲート**。フォーム停止中も標準実行を独自禁止しないため、利用者が部分適用sourceを実行する可能性まで防げるとはしない。保証に操作方針変更が必要なら、具体案をレビューへ戻す。

Undo／Redoは標準APIの操作結果を再読し、新stateRevision・actionGenerationを発行する。文字列や保存済みcellIdが前と同じでも古い要求・実行成功は復活させない。source手動編集だけではフォーム値を変えず、次の明示的な確定でフォーム値から生成する。自動的なsource修復は追加しない。

初期化セルはconnectorIdごとに探索し、1つなら再利用、なければ先頭へ通常Pythonセルを挿入する。複数なら勝手に削除／再実行せず、選択更新をconflictにして002-02へ渡す。利用者が移動した既存初期化セルの自動再配置は追加せず、Run Allの順序はNotebook標準とする。

## 7. UI状態と実行観測

HostのsnapshotとUI表示は互いに独立した次の軸を持つ。下書きの変更表示はactive欄と確定値の比較で決め、非表示保持値だけで「未確定の変更あり」とは表示しない。

| 軸 | 候補値と意味 |
| --- | --- |
| `targetState` | `none \| editable \| inactiveNotebook \| lost \| unsupported` |
| `draftState` | Hostは `none \| stored`、UIは未確認入力があれば `localPending` を重ねる。storedはNotebookモデル反映済みで、ディスク保存済みとは言わない |
| `applyState` | `idle \| applying \| failed \| inconsistent` |
| `sourceState` | `notConfigured \| generated \| manuallyEdited \| unknown`。Hostが同じ定義から再生成して比較できる範囲だけgeneratedとする。実行sourceの証明には使わない |
| `executionState` | `unverified \| stale \| current`。初期／再オープン／手動編集はunverified、生成source変更後はstale。currentは現在設定の成功を証明できた場合だけ |

`stored`と`stale`は同時に成立する。入力下書きだけでは現在sourceの実行状態を変えない。確定でsourceが同じでも、設定／定義の意味が変われば実行証明を無効化する。外部ファイル変更監視はせず、カーネル内変数の内容更新もHostは追跡しない。

`executionSummary.success=true` は成功報告の観測であり、実送信source・設定世代の証明ではない。false／undefined、出力消去、空コード、キャンセル、保存済みexecutionOrder／outputからcurrentにしない。実行開始の空要約や現在sourceのhashだけで証明したことにもしない。

静的API調査の範囲では、安全にcurrentへ遷移させる観測経路は未成立。現段階の案は、成功を観測しても対応が不明ならunverified／staleを保持し、UIに「現在設定での実行成功を確認できません」と示す。これは完了仕様の代替ではなく、不明時の保守的表示案。**「現在設定の成功で未更新解除」の要件は残る**。D4と002-02で対応方法を確立するか、表示・操作方針の変更案を利用者に提示して判断を受けるまで、該当部分を適合済み・005-02完了にしない。独自controller・実行wrapper・Python通知・実行中編集禁止で埋めない。

B07〜B09に従い、実行ボタンを押した回数・待機登録時source・キャンセル要求・終了時の空sourceを、独立した実行IDや送信sourceへ置き換えない。要約にsuccessが存在しない場合は、その理由もunknownとして保持する。論理Notebookセッション終了時の要求失効とカーネル停止も別の事実である。これらの追加制約で、単に「変更を見ていない間のsuccess=true」をcurrentの根拠にする案は採用できない。

## 9. 005-04へ渡す正本・生成／同期・配布案

### 9.1 正本の候補と一方向の更新

推奨は **JSON Schema＋ActionDefinitionを機械可読の正本とし、言語別表現を生成する案**。手書きのTSとPythonを別々に同期する案は乖離を検出しにくい。同じTS／Pythonソースを両言語から直接importする案は採らない。JSON Schema方言候補は2020-12、実際のvalidator／generatorと対応範囲は005-04で選定する。

| 正本候補 | 所有者・意味 | 生成／配布先候補 |
| --- | --- | --- |
