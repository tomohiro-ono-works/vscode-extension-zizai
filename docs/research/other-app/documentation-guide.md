# ドキュメント管理

このファイルは、ZizAIのドキュメント構成とTaskの記載形式を定める正本です。

- 更新日: 2026-10-05

<a id="work-structure"></a>
## 作業の構造

`Project → Objective → Task → Subtask → Step`

- **Project**: 製品、リポジトリ、およびそこで管理する資産全体。
- **Objective**: Project内で達成する、上位の成果。
- **Task**: 独立して完了できる１つの成果。その達成に必要な設計・実装・検証・修正を含む。
- **Subtask**: Taskを実行可能な作業に分けたもの。親Taskを継承し、担当成果・依存関係・検証の詳細を記録する。範囲と管理項目は親TaskのSubtask表で管理する。
- **Step**: Subtask内の具体的な作業手順。

この階層は作業の構造を表し、Agentの割り当てを表すものではありません。完了済みの記録にある`Work Package`／`WP`という用語は履歴として有効です。新規または再開する作業では`Subtask`を使います。

<a id="document-responsibilities"></a>
## ドキュメントの役割

| 配置先 | 役割 | 参照する場面 |
| --- | --- | --- |
| `features/` | 現行仕様、アーキテクチャ、Project共通の実装・検証契約 | 実行中のTaskが参照するファイルだけを読む |
| `tasks/active/` | 現在のTaskの作業権限・状態・残作業・完了条件 | 作業を進めるための主な指示として読む |
| `tasks/done/` | 完了済みTaskの履歴と実施根拠 | 過去の根拠が必要な場合だけ読む |
| `decisions/` | 承認済みの、長期的に有効な設計判断とその理由 | Taskまたは現行仕様から該当する判断を参照する場合に読む |
| `investigations/` | 調査結果、分析、その根拠 | Taskや判断に該当する調査結果が必要な場合に読む |
| `designs/` | 実装設計、代替案、提案 | Taskや判断に該当する設計が必要な場合に読む |
| `handoffs/` | 過去の根拠として保持する既存の調査・設計・引継ぎ記録 | 新規の調査・設計資料は専用フォルダへ置く。既存記録は現行仕様として扱わない |
| `codex_development_guide_2026-08-15_v24/` | バージョンを固定した過去の開発ガイド | 現行仕様として扱わない |

現行仕様は`features/`に置きます。期待する振る舞い・制約は承認済みの現行仕様で確認し、現在のコードは実装の現状を確認するために使います。両者の差異は調査・不具合・承認が必要な仕様変更として扱い、コードに合わせて仕様や期待結果を無断変更しません。過去のTaskや引継ぎ記録は履歴とし、採用理由は必要な`decisions/`の該当箇所で確認します。

<a id="document-types"></a>
### ドキュメントの種類

以下の６種類を使います。作業に必要な文書だけを作成し、小さな変更ではTaskと関連テストだけでよい場合もあります。

| 種類 | 目的 | 内容と配置先 |
| --- | --- | --- |
| 現行仕様書 | 承認済みで現在適用されるルールを定める | 振る舞い、契約、責務、アーキテクチャ、制約を`features/`に記録 |
| 決定記録（ADR） | 長期的な方針を採用した理由を説明する | 承認済みの判断、理由、代替案、影響を`decisions/`に記録 |
| Task | 独立して完了できる１つの成果を定義・管理する | 目的、全体の範囲、参照、制約、完了条件、全体の進捗を`tasks/active/`に記録。完了後は`tasks/done/`へ置く |
| Subtask | Task内の担当成果を記録する | 親へのリンク、担当成果、依存関係、検証の詳細を`tasks/active/`のTask専用ファイルに記録。管理項目は親に置き、完了後は親と一緒に`tasks/done/`へ移す |
| 調査／設計資料 | 判断や実装のための根拠・提案を示す | 調査方法・結果・分析は`investigations/`、実装設計・代替案・提案は`designs/`に記録。既存の`handoffs/`は履歴として保持し、これらの資料単独では現行仕様にならない |
| テスト定義 | 振る舞いを確認する方法を定める | 自動テストのコード、手動の手順、期待結果、合格条件をリポジトリの`tests/`に記録。手動テストの規約は`tests/manual/README.md`を参照 |

要望や改善希望は、その時点では現行仕様ではありません。Taskの背景・目的に記録し、詳しい説明が必要な場合は調査／設計資料に記録します。設計資料が承認されても、自動的に現行仕様にはなりません。仕様の更新が許可されたときに、承認済みのルールを担当する正本の仕様へ反映し、長期的な採用理由は必要に応じてADRに記録します。

READMEは各文書への案内と利用方法を示します。実行ログ、キャプチャ、詳しい実行結果は根拠となる成果物であり、別の文書種別ではありません。

記入用テンプレートは[ドキュメントテンプレート](templates/README.md)に、文書の種類ごとに１ファイルで管理します。テンプレートは記入を補助するもので、ルールの正本はこの文書と各領域の正本です。

<a id="common-document-fields"></a>
### 共通項目

- `ラベル`: 後述する領域ラベルを`#key/value`形式（例: `#領域/値`）で１つ以上記録します。キーは`領域`とし、半角`#`と`/`を使います。複数指定はカンマで区切ります。例: `#領域/フロント, #領域/ブリッジ`。文書が実際に扱う内容から選びます。Subtaskには担当領域を記載し、無関係な親のラベルをコピーしません。
- `リファレンス`（関連ドキュメント）: 参照先の文書、関係する節・要件・決定ID、現在の話題や判断との関係を記載します。名前・フォルダ・ラベルが似ているだけの資料は含めません。使用できる場合は、安定した見出しやIDで該当箇所を示します。
- Subtaskは親へリンクし、共通の参照を継承します。追加または具体化する参照だけを記載し、継承する参照も担当成果に関係するものを使用します。
- 各領域で対応している形式を使います。手動テストYAMLのラベルはコメント、関連ドキュメントは既存のチェックポイントの`refs`文字列へ記載できます。別のテスト形式や未対応のメタデータ項目は追加しません。

<a id="document-writing-style"></a>
### 本文の書き方

- 基本: 箇条書き、短文のキーバリュー（`キー: 値`）、体言止め。
- キー候補: `対応`、`理由`、`例外`、`条件`、`留意`など。厳密な固定項目にはせず、内容に合うキーの追加・言い換え・省略を許容。不要な項目や空欄の作成は不要。
- 階層: 条件と対応、例外と適用条件など、関係を明確にする場合だけ使用。例外がなければ例外項目の省略。
- 情報の保持: 現在の判断、将来の条件、承認主体・時点、適用範囲の区別。短文化による条件・理由の欠落を避けるため、必要な文章説明の併用。
- 表形式: リファレンス、サブタスク一覧、比較など、一覧性が必要な情報での使用。

本文のキーは柔軟に選びます。文書の見出し・必須項目、ラベルの`領域`キーは、それぞれの記載ルールに従います。

書式例:

```md
- 対応: 新しいエラーコードの追加不要
- 理由: 既存コードで要件を表現可能
- 例外:
  - 条件: 既存コードでは表現できない要件が生じた場合
  - 対応:
    - 新規コードと互換性への影響の提示
    - オーナー承認の取得後に追加
```

<a id="task-contract"></a>
## Taskの記載ルール

新規または整理するTaskには、次の見出しを使用します。既存の英語見出しは、該当Taskを整理する際に対応する表記へ変更します。参照されている見出しIDは維持します。

- `ゴール`（目的）
- `スコープ`（対象範囲）
- `スコープ外`（対象外）
- `リファレンス`（関連ドキュメント）
- `制約`
- `完了条件`

次の項目は必要な場合だけ追加します。

- `編集スコープ`（編集範囲）
- `決裁者評価レベル`
- `承認`
- `検証方法`
- `サブタスク`（サブタスク一覧）
- `ステータス`（状態）
- `エビデンス`（実施根拠）
- `残タスク`（残作業）

ゴールはTask全体の達成目標、アウトカムはSubtask完了時に実現される状態・成果を示します。アウトカムには「修正する」などの作業内容ではなく、「不具合の解消」などの達成結果を書きます。Subtaskでは`アウトカム`、必要な先行作業を示す`ディペンデンシー`、`リファレンス`、`完了条件`を使います。Subtaskの完了条件には確認方法と合格条件も含めます。個別の依存関係や追加参照がなければ、その項目は省略できます。

Subtaskには親Taskの参照・制約を繰り返し記載しません。固定の担当者、割り当て理由、工程別のAgent・モデル指定、重複した並列化の管理項目はTaskの記載形式に含めません。保留中のTaskは再開まで旧構成を保持でき、完了済みのTaskや実施根拠を用語統一だけのために書き直しません。

<a id="task-and-subtask-separation"></a>
### TaskとSubtaskの分担

- 親Taskは簡潔にし、全体の目的・範囲・対象外・参照・制約・完了条件を管理します。Subtaskがある場合は、`サブタスク`、`優先度`、`ステータス`、`種別`、`範囲`の表を追加し、サブタスク名をファイルへのリンクにします。全体の状態や実施根拠の要約は必要な場合だけ追加します。
- 作業を分割する必要がある場合にSubtaskを別ファイルにします。各ファイルは親へリンクし、担当成果・依存関係・完了条件・検証方法と結果を記録します。Task固有の参照は、親と異なるものだけ記載します。
- 各Subtaskの優先度・ステータス・種別・範囲の正本は親Taskの表です。種別はSubtaskの主目的（調査・設計・実装・検証・不具合修正など）を示し、この表だけに記録します。Task全体に種別項目は追加せず、工程・種別をラベルへ含めません。Subtaskファイルにこれらの管理項目を重複させません。範囲・編集許可の差分も親へ記録します。表は実際の進捗と検証根拠に基づき更新し、未実施の作業を完了扱いにしません。
- Task全体の作業権限は親Taskが定めます。Subtaskは親の参照・制約を継承し、独自に範囲を拡張したり仕様変更を許可したりできません。
- Subtaskの作成はSubagentの作成を意味しません。可能な限り、１つのAgentが調査・実装・検証・修正まで担当します。委任する場合は、必要な入力が揃い、編集範囲が競合せず、独立して完了できる作業に限定し、親Taskと担当Subtaskを明示して渡します。
- 小さなTaskにSubtaskは不要です。形式を埋めるために空ファイルや同じ要件の繰り返しを作りません。

Taskごとに`tasks/active/TASK-NNN/`を作り、親を`TASK-NNN.md`、Subtaskを`SUBTASK-01-<outcome>.md`として同じフォルダへ置きます。小さいTaskは親の１ファイルだけで開始し、Subtaskや決裁ログは必要になった時点で追加します。調査書・設計資料は種類別の配置先を維持し、Taskからリンクします。

参照はリポジトリ相対パス、または各ファイルの場所から解決できる相対リンクを使用します。完了後はフォルダごと`tasks/done/TASK-NNN/`へ移し、リンクを確認します。完了条件が未達のまま親Taskを完了扱いにしません。既存Taskの配置は、該当Taskを整理する機会に適用し、完了済み記録を配置統一だけのために移しません。

<a id="qa"></a>
### 質問表（QA）

- 用途: Taskの遂行に必要な不明点と、質問・回答・反映先の管理。必要な場合だけ親Taskと同じフォルダに`QA.md`を作成し、親からリンク。
- 質問表: 見出しの直前に`<a id="qa"></a>`を記載。
- 回答欄: 未回答時は`未回答`、回答後は回答の要点・回答日を記載。
- 管理項目: 質問ID、質問日、対象、質問、回答・回答日、状態、反映先。
- 判断: 不明点を推測で確定せず質問。回答が必要な変更だけ保留し、独立して進められる作業は継続。
- 反映: 確定内容は適切な正本へ記録。QAには回答の要点と反映先を残し、詳細の重複を抑制。回答済みの内容を未回答へ戻すことなし。

記入例:

```markdown
<a id="qa"></a>
## 質問表

| ID | 質問日 | 対象 | 質問 | 回答・回答日 | 状態 | 反映先 |
| --- | --- | --- | --- | --- | --- | --- |
| QA-001 | YYYY-MM-DD | 対象 | 確認したい内容 | 未回答 | 回答待ち | 未確定 |
```

<a id="identifier-allocation"></a>
### IDの発番

制定日: 2026-10-04。

| IDの構成要素 | 形式 | 例・発番単位 |
| --- | --- | --- |
| Task番号 | ３桁ゼロ埋め | `038`。`001`から順に発番し、Project内で一意にする |
| Subtask番号 | ２桁ゼロ埋め | `01`。`01`から順に発番し、親Task内で一意にする |
| 決裁日 | ８桁の`YYYYMMDD` | `20261004`。オーナーのタイムゾーンでの実際の決裁日 |
| 決裁連番 | ２桁ゼロ埋め | `01`。Task番号・Subtask番号・決裁日の組み合わせごとに`01`から発番する |

ファイル名と見出しには`TASK-038`、`SUBTASK-01`を使用します。Task外からSubtaskを参照するときは、親Taskも明示します。決裁IDは数字の構成要素だけで`038-01-20261004-01`とします。複数Subtaskにまたがる決裁を含め、Task全体の決裁にはSubtask番号`00`を使い、`038-00-20261004-01`とします。`SUBTASK-00`を実行する作業として発番しません。

発番前に既存IDを確認し、完了・取り下げ後も発行済みIDを再利用しません。この形式は新規発番に適用します。英字のSubtaskを含む既存IDは履歴の識別子として有効なまま保持し、自動で番号を振り直しません。オーナーが数字への変更を明示した場合は、未クローズの親Task内で重複しない２桁番号へ対応付け、ファイル名・見出し・現在の参照を同時に更新します。旧工番の復元可能な対応と、過去の証拠ID・決裁ID・参照用アンカーを保持します（2026-10-04追記）。過去の決裁日を推測したり、文書作成日・移行日を決裁日として付けたりしません。

<a id="area-labels-and-approval-scope"></a>
### 領域ラベルと承認範囲

領域ラベルは影響する責務を示します。次のラベルを１つ以上使用します。ラベルだけで担当責務・編集範囲・承認の深さは確定しません。担当する仕様と正本の更新経路を別途確認します。

| ラベル | 責務 |
| --- | --- |
| #領域/JS／CSS独自プラグイン | Project独自の再利用可能なJavaScript／CSSライブラリ・プラグイン。正本のソースと対応する同期経路を含む |
| #領域/フロント | 画面・表示・入力・操作・画面遷移、UI側の統合 |
| #領域/ブリッジ | フロントエンドとアプリ本体の通信、API・メッセージ、入出力・エラー、通信境界の保護 |
| #領域/アプリ本体 | アプリケーションの起動処理、Desktop／CLIの統合、実行時のライフサイクル |
| #領域/実行BAT | Windowsの起動スクリプトと、呼び出し・引数の契約 |
| #領域/エンジン | ワークフローの実行とコアロジック |
| #領域/コネクタ | 外部システム、ファイル形式、OS操作へのアダプター |
| #領域/横断 | 複数の責務領域にまたがる変更。判明している対象領域のラベルも併記する |
| #領域/マネジメント | 文書管理、Task／Subtaskの運用、承認ルール、Agentの作業割り当て |

フロントとブリッジを両方変更する場合は`#領域/フロント, #領域/ブリッジ`を付けます。フロントが既存ブリッジを呼び出すだけで、通信の契約・処理・境界を変更しない場合は、その呼び出しだけを理由に`#領域/ブリッジ`を付けません。担当する仕様と実際の変更内容に基づいて選びます。

<a id="オーナー評価レベル"></a>
### 決裁者評価レベル

更新日: 2026-10-04。

決裁者評価レベルは、Taskの成果をオーナーがどの深さで評価して承認するかを示します。個々の実装判断の担当、委任する権限、Taskの承認条件を変更する項目ではありません。決裁者による評価が必要な場合に、親Taskへ`決裁者評価レベル`として記録し、Subtaskは継承します。異なる設定が必要な場合も親に記録し、該当Subtaskから参照します。

| 評価レベル | オーナーが評価する内容 | Codexが提示するもの |
| --- | --- | --- |
| 外部設計 | UX・画面・操作・振る舞い・利用者への影響・データ保全が期待を満たすか | 操作例、画面、観測できる影響、検証結果、残るリスク |
| 内部設計 | 責務分担、モジュール、API・IF、データの流れ、連携方式、ライブラリ選定が妥当か | 構成・処理の流れ、契約、代替案、選定理由、互換性・性能の根拠 |
| 詳細設計・実装 | 具体的なアルゴリズム、処理ロジック、コード、メモリ処理が妥当か | 関係するコード・疑似コード、境界条件、測定結果、実装の理由 |

オーナーは通常、外部設計または内部設計レベルで評価し、ソースコードのレビューは基本的に行いません。コネクタは内部設計、セキュリティは外部設計での評価を基本方針とします。内部設計は平易な言葉と具体例で説明し、評価前の質問に対応します。これらは出発点となる方針であり、適用するレベルをTaskへ記録します。領域ラベルから承認・変更責務・作業権限を推測しません。

どの評価レベルでも、技術的な設計・実装品質・必要な検証はCodexが責任を持ちます。セキュリティを外部設計レベルで評価する場合も、承認済みのセキュリティ要件を技術的な仕組みが満たすことをCodexが検証します。オーナーの評価の深さと技術文書の深さは別です。外部設計で評価する場合も、必要な実装根拠を残します。

承認範囲を明確にする必要がある場合は、Taskに簡潔な`承認`を追加します。オーナーが決める事項、Codexへ委任する事項、承認時点・必要な根拠、現在の承認条件と決裁ID・リンクを記録します。詳しい決裁履歴は決裁ログに置きます。評価レベルは説明の粒度を示し、権限は明示した承認範囲で定めます。評価レベル・ラベル・項目の省略から承認済みとは推測せず、既存のTask制約とProjectの決裁ルールを適用します。

Codexは承認範囲内の実装詳細を選択・検証します。利用者影響の評価によって、技術・セキュリティ・検証の要件が免除されることはありません。オーナーが評価できる形で実装根拠と残るリスクを説明します。新たなオーナー決裁事項、承認済みの影響・設計の重要な変更、許可範囲外の判断には追加承認を求めます。既存の承認で許可された通常の作業は、承認を繰り返し求めずに進めます。

<a id="approval-boundaries"></a>
#### 承認境界の基本パターン

- 制定日: 2026-10-05。[TASK-044の決裁](tasks/done/TASK-044/approval-log.md#044-00-20261005-02)
- 適用: Taskの許可範囲・現行仕様・個別承認の内側。領域と工程は代表例であり、実Taskの担当仕様と編集経路を別途確認。
- 区別: 設計対象の技術的な階層と、オーナーが評価する深さは別。認証の構成変更が内部設計でも、オーナーの評価は外部設計とできる。

| 判断対象 | 代表的な領域 | 判断する工程 | 決裁者評価レベル | 分担 |
| --- | --- | --- | --- | --- |
| 承認済みの保存操作などへ戻す不具合修正 | #領域/フロント | 不具合調査・修正方針 | 外部設計 | 修正を許可されたTask内でCodexが対応 |
| 手動保存から自動保存など、操作・保全の変更 | #領域/フロント, #領域/アプリ本体 | 設計・仕様変更 | 外部設計 | オーナーが判断 |
| エラーコードの分類・意味・対処 | #領域/ブリッジ | 初期IF設計・共有・問題時の再設計 | 内部設計 | 初期案はCodex、設計上の問題時はオーナーが判断 |
| データ処理ライブラリの置換 | #領域/エンジン | ライブラリ選定・設計 | 内部設計 | 比較・互換性・メモリ／性能の根拠をCodexが提示し、オーナーが判断 |
| 結果保持のメモリ／一時ファイル、保存先・寿命の変更 | #領域/エンジン, #領域/アプリ本体 | 保持・ライフサイクル設計 | 内部設計 | 方式・保全・機密データ・性能の影響をCodexが提示し、オーナーが判断 |
| 承認済みの認証方式・保護条件・操作を維持する内部整理 | #領域/ブリッジ | 内部設計・実装・検証 | 外部設計 | Codexへ委任。保護条件・操作に変更が必要ならオーナーへ相談 |

- エラーコードの共有: Codexがコード・意味・発生条件・利用者向け文言・対処を整理して共有。必要な処理箇所を確認できる参照を提示。分類不足・意味の曖昧さ・誤った対処への誘導は、原因・選択肢をCodexが示し、オーナーが方針を再設計。合意した設計との不一致は、許可範囲内でCodexが修正・再検証。
- セキュリティ品質: オーナーに内部方式の専門的判断を求めることを前提にせず、Codexが[目標品質・比較・検証](features/coding-rules.md#security-quality-target)を具体化。オーナーは利用前提・保護方針・利用者影響を評価。

承認の整合性を保つルール（追記日: 2026-10-04）:

- Taskの評価レベルに合わせ、具体的な評価基準と必要な技術的根拠を提示し、オーナーが成果を評価して質問できるようにします。
- 評価レベルと、承認した対象・条件を明記します。観測できる振る舞いの承認を、未評価の内部設計やコードまでオーナーが評価・承認したものとして扱いません。
- 承認を求める前に、関連する既存の制約・承認と提案を照合します。過去の承認と衝突する場合は、以前の条件、変更案、理由、影響を示し、変更の明示的な承認を得ます。維持・変更する条件を記録し、最新の回答が以前の条件を自動的に上書きしたとは扱いません。

Subtaskは親の承認範囲を継承します。親Taskで許可された固有の差分や追加の評価時点がある場合だけ、Subtaskに`承認`を追加します。Task全体の現在の承認条件は親、担当部分の評価根拠はSubtaskに置き、決裁履歴はコピーせずリンクします。提案・評価待ち・実際の承認を区別します。１つの判断や工程の承認は、無関係な作業・リリース・後続の承認条件を許可するものではありません。

<a id="approval-log"></a>
### 決裁ログ

制定日: 2026-10-04。

決裁履歴はTask専用の`approval-log.md`に記録します。例えば`tasks/active/TASK-038/approval-log.md`に、必要になった時点で作成し、完了時はTaskと一緒に移します。これはProjectで管理する決裁記録であり、実行時に生成するログや新たな文書種別ではありません。Task／Subtask本文には現在適用する決定事項・条件と、決裁ID・該当ログへのリンクを残します。

- オーナーが確定した、まとまった方針１件に１つの決裁IDを発行します。同時に承認した関連条件は１件にまとめ、独立して変更できる判断は分けます。通常の実装手順、個々の関数、提案、未回答の質問ごとにIDを発行しません。
- 決裁IDを記録の見出しにし、検索・リンクできるようにします。論点、決定事項・適用条件、決裁者、実際の決裁日、決裁者評価レベル、判断の理由、日付を含む根拠への参照を記録します。決裁日、根拠資料の日付、後日の記録日は区別します。
- 発行済みの記録を保持します。決裁を変更する場合は新しいIDを発行し、以前のIDと、維持・変更する条件を記載します。該当Task／Subtaskの現在の条件も更新し、決裁履歴を黙って上書きしません。
- 通常の作業ではTask／Subtaskの現在の条件を読みます。理由、承認の衝突、決裁変更を調べる場合に、関係するログだけ参照します。ログ全文を通常のコンテキストに読み込んだり、共通の必読参照にしたりしません。
- Project全体に関わる長期的な設計判断は、引き続き`decisions/`のADRへ記録します。各Taskのログに理由を複製せず、該当するADRへリンクします。

<a id="investigation-and-design-records"></a>
### 調査書と設計資料

- 新規の調査書は`investigations/`、実装設計は`designs/`に置きます。主目的で分類し、調査書は事実と根拠、設計資料は承認された成果の実現方法を説明します。設計資料では調査結果を複製せず、調査書を参照できます。どちらも判断を補助する資料という文書種別に含めます。
- 短い結論は担当Task／Subtaskの`エビデンス`に記録します。調査方法・観測・分析・根拠の詳細は調査書、実装方式・設計案の詳細は設計資料へ集約し、Task／Subtaskから参照します。既存の該当資料があれば追記し、新規ファイルは必要な場合だけ作成します。
- ファイル候補: 原因・責務・更新経路・修正の必要性が未確認のファイルは、調査書に候補とした理由・確認事項とともに記録。候補への記載だけでの編集許可なし。
- スコープの区別: Taskの`スコープ`は作業・成果の範囲、`編集スコープ`は確認済みの修正対象・責務・許可する変更・正本の更新経路。修正対象は調査で確認後、Taskの許可範囲と承認条件に従って親Taskの編集スコープへ反映。
- 必要に応じて、調査する問い・範囲、方法・情報源、確認済みの事実、分析・設計案、代替案、未解決事項を記録します。確認済みの事実・提案・承認済みの判断を区別します。
- 調査目的・完了条件、結論、Taskへの影響、承認済みの判断、未解決の阻害事項、資料へのリンクはTask／Subtaskに簡潔に残します。詳細は複製せず、該当資料を参照します。親を短くするために目的・制約・完了条件を補足資料へ移しません。
- 提案や調査結果は実装権限を与えません。変更はTaskに明示された範囲と適用する現行仕様に従います。

<a id="detailed-design-documentation"></a>
### 詳細設計を記録する条件

更新日: 2026-10-04。

すべての実装にMarkdownの詳細設計書を必須としません。通常の実装は正本のコードとテストで振る舞い・処理を表現し、調査・保守・評価に必要な場合に追加の理由を記録します。

| 場面 | 残す詳細 |
| --- | --- |
| 不具合調査 | 再現条件、原因となる処理、修正の理由、再発防止の検証 |
| 複雑な処理 | コードだけでは読み取りにくいアルゴリズム、重要な前提、境界条件 |
| 性能・メモリの調査 | 比較した方式、測定条件・結果、採用理由 |

短い説明は担当Task／Subtaskに置き、詳しい調査結果は調査書、実装方式・比較は設計資料に記録してリンクします。詳細は１つの場所で管理し、他の文書からは該当箇所へリンクします。文書を埋めるためにソースファイル全体、通常の関数ごとの説明、テスト手順・結果を複製しません。具体的な問題や判断の説明に役立つ場合だけ、コード・テストへの参照や短い疑似コードを使用します。

Projectで必須とされた文書や、承認済みのTask成果物は引き続き必要です。決裁者評価レベルにかかわらず、必要な技術的根拠を保持します。その根拠があることを理由に、オーナーへソースコードのレビューを求めません。

<a id="tests-and-execution-evidence"></a>
### テストと実施根拠

- 開発との関係: ケース作成・スクリプト整備・環境別実行・設計変更時の更新順は[開発サイクル](features/coding-rules.md#development-cycle)を参照。文書管理では手順の詳細を重複定義しません。
- 現行仕様が必要な振る舞いを定め、Task／Subtaskが完了条件に必要な検証を選び、テスト定義が手順と期待結果を定めます。
- 再利用する自動・手動テストの定義は`tests/`に置きます。短いTask固有の確認はTask／Subtaskに直接記載でき、別のテスト文書を作成する必要はありません。
- 検証したリビジョン・関係する環境、実行したコマンド・チェックポイント、結果、未実施・失敗・阻害された確認をTask／Subtaskの`エビデンス`へ記録します。未実施の確認を合格扱いにしません。
- 詳しい結果ファイル、ログ、キャプチャは複数文書にコピーせずリンクします。保存・追跡・プライバシーは、担当するテストと実施根拠の規約に従います。

<a id="progress-and-handoff-information"></a>
### 進捗と引継ぎ

新規作業の進捗を渡すためだけに、別の引継ぎ書を作成しません。現在の状態、完了した作業、残作業、阻害事項・未決事項、根拠へのリンク、次の行動を担当Task／Subtaskに記録します。全体の情報は親、担当部分の詳細は該当Subtaskに置きます。

本文には現在の作業・判断に必要な情報を残します。文書の分割・移動・翻訳を行った説明、移動対応表、整理作業だけの検証記録は、通常の作業で読む本文へ残しません。必要な間だけ一時アーカイブに保持し、Git履歴への保存、固有情報の保持、現在の参照先を確認してから削除します。内容更新日・実際の決裁日・実施日を区別し、整理日を製品検証日や決裁日として扱いません。

引継ぎや再開時は、親Taskと該当Subtaskを読み、必要な参照先を確認します。作業を進める記録を、そのまま引継ぎにも使用します。既存の引継ぎ書は履歴として保持し、この構成へ揃えるためだけに書き直したり移動したりしません。

文書管理とTaskの記載ルールは、この文書で管理します。`AGENTS.md`とテンプレートはこの文書へリンクし、必要な参照案内・記入補助だけを持たせ、ルールを重複させません。各テスト領域のREADMEは、その領域固有の実行方法と結果形式を管理します。
