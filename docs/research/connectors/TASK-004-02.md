## 進め方と共通の入力案

推奨は、まず各アクションの基本入力だけを仕様化し、旧schema・クレンジング等の詳細を必要性に応じて追加する案。旧フォームの全項目を再現する案は機能を比較しやすいが、未採用の旧共通基盤まで前提にする項目が多い。先に表読取だけを実装する案では初回7種類の範囲を満たさない。今回は全7種類の対応を保ち、採用範囲の判断材料を作る。

以下のフィールド名は旧資料との照合用の仮名。正式なフォーム・メソッド引数・metadataキーではない。フォーム部品のJSON形式も決定しない。

- path・SQL・project等は文字列。入力表はPython変数への参照名を受け取り、生成sourceでは引用符なしの変数として渡す候補。旧Engineのcontextキーには変換しない。
- 必須欄の初期値は空欄とし、実在するファイルやprojectを保証しない仮の値を自動入力しない。False／0、空文字、None、任意引数の省略を区別する。
- 初期値候補はUI表示とPython呼出しで一致させる。既定値を暗黙に解決するより、確定した値を生成sourceに明示する案。
- 出力先は1つのoutput_path欄へまとめる案を推奨候補とする。旧output_folder＋file_nameを残す案も比較対象。両者の優先規則を黙って持ち込まない。
- 相対pathはカーネルcwd基準とする案を比較する。実行場所がHostと異なる場合のpath変換は未確認。Hostでファイル不在を判定してカーネルの失敗と同一視しない。
- 出力を表として扱う具体ライブラリ、schema、日時・数値変換は未確定。CSV／Excel等で都合よく型を変更・欠落させることを初期値に含めない。

### 明示型への変換失敗：選択可能な3方式

本書の「行分離mode」は、利用者が選択した3番目の処理「変換に失敗したセルを含む行全体を通常dfから除外し、別のエラーdfへ返す」の略称である。セルだけを取り出す処理や別の追加機能を指さない。

利用者は固定の停止方式ではなく「例外で止める／欠損値で続ける／変換できなかった値だけ別dfに集約する」を選択したいと回答し、3つ目について「失敗セルがある行全体を通常dfから除外し、別dfへ」と指定した。現在の対象はC01／E01／E03の明示schemaによる読取時の型変換。C02／E02の書込は、その後の回答に基づき正常／エラーのどちらのdfを保存するか明示する別の責務として整理する。3方式の選択と失敗行全体の分離は採用判断として記録する。固定元の型対応表をそのまま実行すればこの機能が得られるとはしない。

| 利用者が選ぶ方式 | 正常側の扱い | 失敗値・行の扱い |
| --- | --- | --- |
| 例外で止める | 正常結果として返さず、処理失敗とする | 変換失敗を通常Python例外で通知。例外class・詳細情報は正式APIで照合 |

初期選択は利用者回答により「例外で止める」。正式fieldId／keyword・enumの内部値は採用照合前であり、既存actionの実引数として実装しない。方式はセルの型変換失敗を対象とし、不正schema・未存在列・file読書き・encoding・権限等の失敗まで黙示的に欠損化して成功へ変える機能にはしない。元から存在する欠損を失敗として分離するかは、各型の欠損許容規則へ対応付ける。

別dfモードは利用者の「2値でOKです。生成されるコードも 正常とエラーdfを明示して変数定義してください」という回答で2つの結果を返す要件を受領し、その後の利用者の辞書案と明文化の依頼により、読取の返却形をPython辞書へ更新する。キーの綴りは `success` と `errors`。元の例の `succes` は `success` へ訂正し、別名としては定義しない。読取では `{"success": df_success, "errors": df_errors}` とし、関数の戻り値は1つの辞書、その中に正常dfとエラーdfの2結果を保持する。successは成功可否のboolではなく正常行のDataFrameである。JSONへ変換したりHost／metadataへ表本体を送ったりする形式ではない。

書込について利用者は「書き込み時はdfを指定するので、それぞれ別のdfだから、明示的にどちらを選択する必要があります」と回答した。C02／E02のinput_dataにはdf_successまたはdf_errors等、保存したいdfを明示して渡す。書込側がres辞書を判定して正常側を自動選択したり、両dfを自動合算したり、成功dfを返す辞書へ揃えたりしない。従来の保存結果文字列を返す基準は維持する。エラーdfを保存したい場合も、その変数を明示して別に書込む。既存の任意schemaによる書込時再変換を残すかは別の確認事項である。

## 列schema：型変換・正常／エラー行の具体化

この節はC01／C02／E01／E02／E03のschemaを対象とし、SC-01／SC-02／SC-08の採用照合を進める。個別mdの「schemaによる列選択・型・rename」と、利用者が承認した「失敗行を通常dfから除外し、変換前の行全体を別dfへ返す」を併せて扱う。Data IntegrationのRENAME／filterやBigQueryのschema優先順位へ自動展開しない。

### 列選択のレビュー例

以下は架空の入力表を使った期待結果の説明で、実ファイル処理・製品テストではない。入力の値は型変換前に読取済み、または書込へ渡したdfのセル値として示す。CSVの元bytesやExcel表示文字列をそのまま復元した保証ではない。

| 数量 |
| --- |
| 2 |
| 5 |

### schemaの指定状態と処理順序のレビュー案

schema省略・明示null／None・空配列[]を「明示schema指定なし」に揃える案を利用者へ確認中。指定なしの読取は推論、書込は入力表の列・値を使用する原資料の基準を引き継ぐ案である。これは空textやJSON配列文字列まで自動的に指定なしへ変える意味ではない。採用前にnullableや空配列の意味を正式fieldへ確定しない。

利用者から「python側で暗黙型定義ってしたりするの？」という質問を受領した。ここでの「推論」は、読込やDataFrame構築を担うライブラリが値から列の型を推定する意味で、独自のziz_datatype schemaやPythonの型注釈を自動生成する意味ではない。pandasの[CSV読取](https://pandas.pydata.org/docs/reference/api/pandas.read_csv.html)・[Excel読取](https://pandas.pydata.org/docs/reference/api/pandas.read_excel.html)にも列型推定の一般動作が記載されているが、正式な採用版・実装経路・具体dtypeの保証として引用しない。既存Excelコードのopenpyxl経路を、この説明だけでpandas.read_excelへ変更しない。書込では入力dfが既に型を持つため、schemaなしの場合はその列・値を使う案である。今回の質問をschema省略／null／空配列の統一案の承認とはみなさない。

読取の列schemaを明示した場合の処理順序案は、入力／schema定義の検証、変換前の行を追跡できる状態の保持、指定列と型の対応付け、列ごとの変換と失敗行の判定、選択modeに応じた欠損化または行分離、結果の返却である。取込でrenameを行う段階は設けない。列選択の段階・必要性は上の照合事項であり、名称変更を除いた判断から自動確定しない。同じ行の複数失敗を別の入力行に見立てず、行全体として判定する。元dfのindexラベルだけで行を特定すると重複indexで別行まで除外するため、行の対応付け方法を実装前の条件として渡す。

型変換前の値を後から文字列化・逆変換して作り直す案にはしない。列定義に不正がある状態で途中まで保存を始めず、schema／型変換の失敗と保存I/Oの失敗を分けて検証する。これは全保存操作の原子性・rollbackの保証ではない。処理順序と副作用境界、読取parserが先に行う型推論・欠損化・日付変換は003／004／005の対象API確定前に照合する。

採用後に詳細化する条件は、schemaの順序と入力列順が異なる場合、列名入替え、未指定列、未存在列・重複列／出力名、空schema、全行正常／全行失敗と空dfの列、同一行の複数失敗、元dfの非変更、保存対象列とエラーdfの列の違い。これらをSC-01／SC-02／SC-03／SC-08へ対応付ける。fieldId／keyword・型の正式形式、origin_name等の必須／省略条件、文字列schema互換、attrsの扱いは別の残条件として保持する。

## 名称変更と型変換の責務分離

利用者の「カラムの名称変更と型変換はそもそも分けようか。取り込み時は、型変換のみ行う。ことにしよう」により、CSV／Excel取込C01／E01／E03では列名を変更しない。型変換を行った正常dfと、変換前の値を保持するエラーdfは元の列名で対応付ける。読取schemaのnew_nameでrenameする先行案は、この判断に置き換える。型集合・変換失敗3方式・辞書success／errorsと明示的な変数代入は維持する。

この「型変換のみ」を、列選択・推論・行位置等の別の確定／未決事項を変更する承認へ広げない。先に決めた明示列と出力順の扱い、型変換対象列と出力列の区分は関連する未決点として照合する。書込schemaの採用・廃止や書込時再変換の可否も、この取込の判断だけで確定しない。

名称変更の利用者指定は、既存のpandasのdf.rename(columns={...})を使うPythonコードと確認された。「簡単な方法でいい」という意向に従い、標準セルで全カラム名を表示し、変更したい列だけを辞書で指定する簡単な説明形とする。専用フォーム・表編集UI・名称変更用の独自runtime APIは作らない。どのdfへ適用するかは通常のPython変数で明示する。名称変更を呼び出すactionの登録・source生成への接続は対象契約と照合し、今回の説明例だけで製品実装済みとはしない。

利用者は「フォームは不要でdfのrenameできるものがあったと思うので、そちらで全カラムを表示してほしい」「2は別のアクションの話なので、一旦無視」と回答した。全カラム名は選択・確定時にHostで取得せず、標準セルを実行したときにdf.columnsから一覧を出力する。名称変更の辞書に全列を重複して入力する必要はなく、変更しない列はpandasの標準renameに従って元名のまま残る。[DataFrame.rename公式資料](https://pandas.pydata.org/docs/reference/api/pandas.DataFrame.rename.html)でcolumns辞書と未指定ラベルの扱いを確認した。採用pandas版と実環境の適合確認は別に残す。

次は架空の数量→個数を使った普通のPythonコードの説明例である。利用者は先頭の全カラム名を確認し、必要な変更だけをcolumns内に記載する。df_successは説明用の入力変数で、df_errors等へ明示的に変えてもよい。df_renamedも説明用の出力名で、正式な自動命名ではない。取込は型変換、名称変更はこの後段の処理と分ける。コードの構文確認を、実dfやNotebook UIでの実行結果とは扱わない。


利用者の「辞書のみ変数にする形式」に合わせ、名称変更の対応辞書をrename_columnsとして分離する。変更箇所はこの辞書に集約し、標準renameの呼出しへ渡す。rename_columnsは説明用の変数名で、正式な自動命名ではない。success／errorsを保持する読取結果の辞書とは別である。

Pythonコードを使う回答を受け、表編集UIの調査・追加は進めない。全カラム表示を理由に、選択・確定時のPython先行実行やDataFrame本体のHost同期を追加しない。利用するのは既存の標準セル実行とカーネル内の実dfであり、専用Pythonコネクタの追加でもない。
