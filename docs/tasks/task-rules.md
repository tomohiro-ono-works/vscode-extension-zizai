# Task・Subtask の作成ルール

更新日：2026-10-24。

この文書を Task の分類、分割、Issueの関係、記載項目、状態管理の基準とします。実際の開発 Task は、ユーザーの依頼と [アーキテクチャ](../features/architecture.md) にある責務を確認して作成します。

## 作業記録の正本

Task・Subtaskの作業範囲、進捗、判断、結果、残作業はGitHub Issuesを正本とします。[Task索引](README.md)から担当Issue・親Issueを開きます。新しいTask実行記録のMarkdownは作成せず、既存Markdownは移行元の記録として扱います。設計書、調査資料、決定記録、テスト手順・証跡は引き続きリポジトリに保存してIssueから参照します。

現在の親子関係・開始条件・共同検討はIssue本文のリンクとして管理しています。GitHub標準のSub-issue／依存フィールドとProjectsは未設定です。本文リンクをネイティブの登録済み関係として扱いません。

## 1. 領域と工程

Task に主担当領域を1つ記載し、他の領域にも影響する場合は関係領域を併記します。次の6領域を分類の基準とします。

| 領域 | 主な責務 |
| --- | --- |
| VS Code 拡張機能本体 | セル操作、metadata 管理、Python コード生成、初期化セル管理、UI 通信 |
| Notebook UI | 処理選択、入力フォーム、下書き・確定操作、状態・入力エラー表示 |
| Python 共通基盤 | Jupyter 内で利用する Python ライブラリの処理基盤・共通ロジック |
| コネクタ | ファイル形式・外部サービス等に対応する個別アクション |
| 共通契約 | UI／Host 通信、metadata、Python 呼び出しなどの境界仕様 |
| 開発運用・プロジェクト管理 | 開発ルール、Task・資料管理、開発環境、ビルド、CI、結合検証、配布 |

各機能の設計・仕様・単体テストは、その機能の領域に含めます。領域名や配置先だけで編集権限を決めず、担当する正本と Task のスコープを確認します。

工程は、主に Subtask の作業分類として使います。工程は前後・反復して構いません。

| 工程 | 記載する作業と成果 |
| --- | --- |
| 調査 | 事実・制約・不明点を調べ、根拠と判断材料を残す |
| 設計 | 責務、動作、境界、変更範囲、期待結果を具体化する |
| 実行 | ソース、設定、文書、実行手順などを作成・変更する |
| 単体テスト | 個別の関数・モジュール等を独立して確認する |
| 検証 | 完了条件と実際の動作・成果物を照合し、結果を記録する |
| 統合テスト | UI・Host・Python 等の境界をまたぐ一連の動作を確認する |
| CI | 確定したビルド・確認コマンドを継続的に実行できるようにする |

必要な工程だけを用います。全 Task に7工程の Subtask を機械的に作りません。Task 自体が調査だけを扱う場合などは、Task にも工程を記載できます。

この7工程は本プロジェクトで合意した作業分類です。別アプリ由来の `coding-rules.md` にある「調査・設計」から「完了・リリース」までの7段階の開発サイクルとは別に扱います。

## 2. Task と Subtask の分け方

- 基本は領域ごとに Task を作り、そのゴールに必要な具体的作業を工程付きの Subtask に分ける。同じ領域でも、独立して完了判定できるゴールは別 Task にしてよい。
- 親 Task はゴール、全体スコープ、制約、完了条件、Subtask 間の依存関係を管理する。
- Subtask は1つの確認可能な成果を単位にし、主工程を1つ記載する。必要な関連工程も併記できる。
- 小さな作業は Task 本文のチェックリストだけで管理してよい。分割自体を目的にしない。
- 複数の領域にまたがる場合は主担当を明示し、他領域の変更・協力・依存先を記載する。
- 共通契約や同じ成果物の変更は担当する Task に集約し、他の Task は依存先として参照する。

担当者・状態・完了条件を独立して管理するSubtaskは個別Issueにし、親Issueの一覧と子Issueの親参照を相互にリンクします。小さな作業は担当Issue内のチェックリストにします。単に工程が違うという理由だけでIssueを増やしません。共同検討のリンクと、着手を止める先行条件は区別します。

## 3. ID とIssueの関係

- 新規TaskのIDは`TASK-001`のような連番とし、Open／Closed両方のIssueを検索して未使用の番号を割り当てる。
- Subtaskは`TASK-001-01`のように親IDに連番を付ける。領域・工程を変更してもIDは維持する。
- Issue番号とTask IDは別の識別子。タイトルにTask IDを残し、相互リンクはIssue URLを使う。
- 別アプリの参考資料にあるTask番号は本プロジェクトの採番対象に含めない。
- 既存の日付名の完了記録は元記録ID・実施日・原文を完了履歴Issueに保持し、新しい開発Taskとして採番しない。

親Issueはゴールと全体の完了条件、作業Issueの一覧を持ちます。作業Issueは親へのリンクと具体的な範囲・結果を持ちます。完了時は結果と残る影響を記録してCloseし、Markdownフォルダーの作成・移動を状態管理に使いません。

## 4. 作成前の確認

1. 依頼の目的と、既存 Task に同じ作業がないかを確認する。
2. 関係する全体設計・個別仕様・責務を読み、主担当領域と影響領域を確認する。
3. 変更候補を正本、統合部分、外部由来のコピー、生成物などに分類し、所有者・更新経路を確認する。不明なものは未確定と明記する。
4. ゴール、スコープ、制約、完了条件を依頼の範囲で定義する。
5. 開始条件、依存 Task／Subtask、必要な環境・認証・判断を記載する。下記の区分で、必須の前提条件と相互確認先を明記する。
6. [Task本文のひな形](../../template/task.md)または[Subtask本文のひな形](../../template/subtask.md)を使ってIssueを作成する。親子・参照先を相互リンクし、新しい親Taskは`docs/tasks/README.md`の入口へ追加する。状態は索引に二重管理しない。

具体的な API、ファイル名、依存バージョンなどが未定の場合は、設計 Subtask の成果として確定する。未確定事項があることを隠して実装可能な計画として扱わず、影響を受けない調査・準備は進めてよい。

### 開始条件・依存関係の区分

Task・Subtaskの作成・更新・着手判断では、Issue本文の「開始条件・依存関係」（既存Issueの「開始条件・関連タスク」も同じ）を次の区分で記載する。各区分に該当がなければ「なし」とする。

| 区分 | 記載する内容 | 進行の判断 |
| --- | --- | --- |
| 必須の前提条件 | 相手のTask／Subtask ID・Issue URL、必要な具体的成果と対象部分、必要になる工程（着手／確定／検証／完了等）、充足状況・根拠、未充足時の再開条件 | 必要な工程と対象部分に限定して条件を適用する。相手Task全体の完了が必要か、対象部分の成果で足りるかを明記する |
| 相互確認先 | 相手のTask／Subtask ID・Issue URL、すり合わせる仕様・契約・責務境界、確定前でも独立して進められる範囲、照合が必要な時点 | 案の作成や独立した確認は並行できる。必須の前提条件もある相手は、その条件を別の行で明記する |
| 区分未確定 | 関連するTask／Subtask、分類できない理由、確認すべき点と担当、影響する工程・範囲 | 未確定の条件に影響されない作業は継続する。区分や依存の充足を推測しない |

必要な環境・認証・判断は上記の関係と併記する。実機確認が条件なら、対象版・環境、未実施の確認項目、CLIで進められる範囲とユーザーのUI操作が必要な範囲を区別する。秘密値は記載しない。

既存Issueへ適用するときは、最新の成果・判断・コメントを確認し、現在の依存関係欄を整理する。過去の結果・承認・失敗証跡は保持する。単に参照リンクがあることを理由に必須条件へ変更したり、既存の必須条件を相互確認へ移して外したりしない。条件の追加・削除・強弱の変更は、既存の依頼・仕様・判断に根拠がある場合だけ反映し、その根拠を記録する。分類だけでは作業権限・完了条件・承認範囲を変更しない。

相手側の更新は担当Taskへ受け渡し、担当外のIssue・コードを無断で変更しない。親Issueの一覧には区分を示し、詳細・充足状況は担当Subtask Issueを参照して二重管理を避ける。

## 5. 記載項目

| 親 Task の項目 | 記載する内容 |
| --- | --- |
| 基本情報 | ID、名前、状態、主担当領域、関係領域、主工程・関連工程。移行時は元Task更新日も保持 |
| Goal（ゴール） | 何ができる状態・何が判断できる状態になるか |
| Scope（スコープ） | 対象作業、編集領域と許可する操作、閲覧領域、対象外、正本・更新経路。リポジトリ相対のフォルダ・ファイルを明記 |
| 設計レベル | 外部設計（利用者の動作・入出力）、内部設計（責務・構造・状態）、詳細設計（実装単位の規則・処理・例外・確認条件）、または対象外 |
| Constraints（制約） | 正本、互換性、実行環境、変更できない条件 |
| Acceptance Criteria（完了条件） | 観測・確認できる期待結果 |
| References（関係資料） | 着手時に必要な仕様・設計・決定・コードへのリンク |
| 開始条件・依存関係 | 必須の前提条件・相互確認先・区分未確定を分け、必要な成果・工程・充足状況、環境、判断・承認を記載 |
| Subtasks | ID、工程、作業名、開始条件、成果物・完了条件、状態 |
| 評価・承認 | 必要な判断、依頼による許可範囲、実際に得られた判断の根拠 |
| 実施・結果 | 対象版、環境、手順、結果、証拠、残作業 |

親に共通する条件は一度だけ記載し、Subtask は親を継承します。各 Subtask では具体的なゴール、追加のスコープ・制約、開始条件、成果物・完了条件、手順・結果を記載します。独立した結果や作業記録を追えるよう、親子IssueのIDとリンクを一致させます。

Task のスコープは作業権限の根拠です。依頼や既存の許可で認められた通常作業を進め、必要のない再承認を要求しません。仕様・制約の変更や外部への公開など、既存の許可を超える判断が必要な場合は、その具体的な内容を確認します。一般的な「続けて」を、仕様変更の追加許可として解釈しません。

## 6. 状態と完了判定

Task・Subtask の状態は `未着手`、`進行中`、`保留`、`完了`、`中止` を使います。保留時は理由と再開条件、中止時は理由と後続作業を記載します。状態は担当Issueのラベル・本文で管理し、Open／Closedだけで未着手・進行中・保留を混同しません。完了はClosed/completed、中止は理由を記録してClosed/not_plannedとします。開始条件の未充足は、未着手の Task にも記載できます。

- Task の必要な Subtask と完了条件を満たし、結果を記録してから完了にする。
- 確認の結果は `合格`、`不合格`、`未実施`、`対象外` を区別する。対象外には理由を残す。
- 必須の確認が未実施・不合格のまま、完了にしない。完了条件を変更する場合は理由と許可の根拠を記録し、過去の結果を書き換えない。
- 調査 Task は、実現不可や不足情報の特定がゴールを満たす場合もある。Task 完了、製品の動作成立、出荷判断をそれぞれ記録する。
- クラウドの確認と、デスクトップの VS Code／Jupyter での確認を区別する。必要なデスクトップ確認をクラウドの結果で代替しない。
- 対象ブランチ・コミット、未コミット差分、環境、実行コマンドまたは手動操作、期待結果と実際の結果を記録する。長いログ・画像は成果物への参照にする。

テストの定義・手順はテストコードや `tests/manual/` を参照し、Task に全文を重複させません。Task には実施結果と根拠を残します。文書変更ではリンク・配置・差分など、その変更に合う確認を行います。

## 7. 文書の役割

- README・資料索引：目的、入口、資料の位置づけ、Task の所在を示す。
- 現行仕様・設計：担当機能の動作・責務・境界を定義する。未決定事項と決定事項を区別する。
- Task・Subtask：作業範囲、進行、判断、結果、残作業を記録する。製品仕様の唯一の置き場にしない。
- 決定記録：実際の判断・承認と理由を残す。
- 調査・参考資料：調べた事実と出所を記録する。別アプリの仕様・実装・Task・承認を今回の正本として採用済みと扱わない。

ルールの整備、Issueの作成、作業への着手は区別します。現在の状態・判断・残作業は担当Issueを正本とし、索引と旧Markdownには二重管理しません。GitHubの更新日時と、移行元のTask更新日・実施日は別の情報として保持します。
