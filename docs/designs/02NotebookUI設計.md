# 02 Notebook UI詳細設計 — Zizai

更新日：2026-10-25

対象：VS Code / Kiro IDE 上の Jupyter Notebook（`.ipynb`）  
状態：2026-10-22の利用者選択により、詳細フォームの配置方針をサイドバーへ変更。下記の12項目も配置に合わせて更新した。対象切替・表示・通知の[サイドバー設計](../features/notebook-sidebar.md)は2026-10-23に利用者が承認済み。API依存部分と製品の動作は技術検証待ち。

## 1. 目的・適用範囲

Notebook標準のPythonコードセルと実行基盤を活用し、セル内でコネクタ・アクションを選び、アクション固有フォームからPythonコードを生成できるUIを定義する。本書は共通Notebook UI、セル表示、編集・保存・状態遷移、Extension Hostとの概念I/Fを扱う。各アクションの引数、処理、Python APIシグネチャ、結果データの詳細は対象外とする。

優先順位は [01全体設計.md](01全体設計.md)（正本）→ 本書で確定したNotebook UI詳細 → [DESIGN.md](DESIGN.md)（全体設計と重複する参考資料）の順。本書は全体設計を無言で上書きしない。とくにフォーム下書きのmetadata保存は、本設計で追加する詳細仕様として明示する。

## 2. 前提・変更しない全体設計

- `.ipynb`、Notebook標準のセルsource・metadata・出力、標準のセル実行・Run All・Python例外表示を使う。
- 拡張機能側は独自カーネル、実行サーバー、Run All、DataFrame同期、独自結果ページネーションを作らない。
- UI（セル側の選択UI・サイドバー）は表示・入力・イベント通知に限定。Extension Hostはmetadata・セル編集・Python生成・初期化セル管理を担う。生成コードの実行は既存Jupyterカーネルが担う。
- コネクタ選択・アクション選択は確定ボタンなしで即反映。アクション固有設定をPython sourceへ適用するのは確定ボタン押下時のみ。どちらの操作もPythonを実行しない。
- コネクタごとに独立した初期化用通常PythonセルをNotebook先頭へ必要に応じて作り、同一コネクタでは再利用する。単独実行前の初期化セル実行はユーザー責任。
- 元PythonコードはExtension Hostの一時メモリに退避し、Notebookを閉じたら破棄する。永続バックアップは作らない。
- セル出力は標準Notebookに保存され得る。前回結果を残して「未更新」を示し、再実行成功で解除する。外部ファイル変更は監視しない。
- 初回7コネクタ：CSV、Excel、DuckDB、BigQuery、Python、Data Integration、Shell。次回：Plotly、Chrome、Windows。低優先度：Vector、Selenium、独自結果UI。

## 3. 用語とセル種別

UIの呼称は、利用者と合意した [HTMLフォーム／セルツールバーの整理](../decisions/2026-10-19-notebook-ui-terms.md) に従う。今回の「セルにボタン／プルダウンを追加する」という話はセルツールバーの選択メニューを指す。以下の従来のHTMLフォーム配置案と区別し、セルツールバーの操作までHTMLフォームの常設条件で判断しない。この呼称整理自体は配置変更の根拠ではない。詳細フォームのサイドバー配置は別途得た[2026-10-22の利用者選択](../decisions/2026-10-22-notebook-sidebar.md)に基づく。

| 用語 | 意味 |
|---|---|
| HTMLフォーム | HTMLで描画する入力欄・プルダウン等。セルツールバーとは区別する |
| セルツールバー | Notebookのセルの操作ボタンと、そこから開くメニュー。Zizai拡張のUIの一部 |
| コネクタ/アクション選択プルダウン | コネクタとそのアクションを選ぶセル内UI。Python選択も含む |
| アクション詳細設定フォーム | 選択したアクションに必要な入力を編集・確定するUI |
| Pythonセル | ユーザーが任意のPythonコードを書く通常コードセル。Python選択時にフォームとアクション選択は不要 |
| 処理セル | Zizaiのコネクタ／アクションが設定された通常Pythonコードセル。生成sourceと、サイドバーに表示するセル別のフォーム設定を持つ |
| 初期化セル | importとインスタンス生成を持つ、Zizaiが自動管理する通常Pythonコードセル |
| 確定済み設定 | 最後に「確定」によりPython生成sourceへ反映されたフォーム値 |
| 下書き | 入力中で未確定のフォーム値。生成sourceにはまだ反映されない |
| 未更新 | 設定反映後に、現在の設定によるセルの再実行成功を確認していない状態 |

※「Python」選択と「Pythonコネクタ」のアクション選択は別概念。前者は通常Pythonセル、後者はコネクタ操作である。表示ラベルで混同しないようにする（具体的なラベル案は実装前に確認）。

## 4. セルUI構成・レイアウト

### 4.1 処理セルとサイドバー

セル側にはコネクタ／アクションの共通選択UI、対象セルの設定を開く操作、標準Python source、標準の実行結果／例外を置く。詳細フォーム・状態表示・確定ボタンはサイドバーへ移す。独自のコード非表示・折りたたみや結果ビューを加えない。

サイドバーは1つの設定欄で対象セルのフォームを表示する。フォームを表示している間は独自の折りたたみを設けず、通常のサイドバーの開閉・移動はIDEに委ねる。全処理セルのフォームを同時に常設する条件は終了する。

```text
Notebook                           ZizAI サイドバー
┌ 処理セル ──────────────────┐    ┌────────────────────────┐
│ 共通処理選択UI  [設定]      │    │ Notebook名 / セル / 処理 │
│ 標準Python source          │    │ [未更新]／[下書き]       │
│ 標準の実行結果・例外        │    │ 項目名                   │
└───────────────────────────┘    │ [入力欄]                 │
                                 │ 入力エラー               │
                                 │                  [確定]  │
                                 └────────────────────────┘
```

対象の開き方・切替・下書きの保持・対象喪失時の表示は[サイドバー設計](../features/notebook-sidebar.md)に従う。セル側の共通選択は、2026-10-25の利用者判断により、通常Pythonと各コネクタの処理を1つのメニューにまとめる。[判断記録](../decisions/2026-10-22-notebook-sidebar.md)を参照。正確なラベル・ボタン位置は後続の対象仕様・実機確認と整合させる。

### 4.2 Pythonセル

Pythonを選んだ場合は通常のPythonコード入力として扱い、**アクション選択欄とアクション詳細設定フォームを表示しない**。Pythonへ戻すための共通選択UIの表示方法は、セル切替可能性と整合する方式を技術検証する。元コードの復元は同じNotebookを開いている間の一時退避が存在する場合に限る。

### 4.3 初期化セル

**コネクタ/アクション選択プルダウンとアクション詳細設定フォームをどちらも表示しない（質問⑫：A）。** 通常Pythonコードセルとして表示し、標準の実行・出力・折りたたみ機能を使う。初期化セルは既存の重複防止・再利用のためにも識別が必要。具体的な識別キー、移動・複製に対する検知は技術検証対象。

## 5. UI部品の役割

| コンポーネント | UIでの責務 | 責務外 |
|---|---|---|
| 選択プルダウン | Python/コネクタ/アクション選択、選択イベント通知 | Python生成・実行 |
| 詳細フォーム | アクション定義に従った入力表示、下書き編集、値収集 | セルsource直接編集・実行 |
| 確定ボタン | 入力検証後に適用イベント通知 | Python実行 |
| エラー表示 | 不正項目直下への検証メッセージ表示 | Python実行例外の独自表示 |
| 未更新ラベル | 最新の反映設定で再実行が必要な状態を表示 | 実行を起動すること |
| Extension Host | 保存・コード生成・セル編集・UIへの状態配信 | 業務データ処理・Jupyter実行 |

フォームのデザイン・基本部品は `https://github.com/tomohiro-ono-works/zizai-form` の NodeFormを参考にする。フォーム定義からの生成、`getParams()`、`setParams()`、`validate()`、`visible_if`、ファイル/フォルダ選択イベントが再利用候補。ただし、サイドバーでの読込・ライフサイクルとNotebook連携を検証するまで、製品への全面採用・直接移植を確定しない。評価用WebviewのWindows実機結果は[TASK-001-02](https://github.com/tomohiro-ono-works/vscode-extension-zizai/issues/9)を参照する。ファイル選択等のOS操作はExtension Hostが担当する。

## 6. 入力・確定・切替の振る舞い

### 6.1 コネクタ/アクション選択（質問①・⑤）

- セル側の1つの共通メニューで通常Pythonまたは各コネクタのアクションを選択する。選択直後に該当UIと必要な生成コードを反映する（全体設計の即時反映）。
- `Python` は通常Pythonセルへの切替であり、アクション詳細設定の対象ではない。
- 処理セルのアクションを切り替える場合は、以前のアクションの未確定・確定済みのフォーム値を保持しない。新しいアクションの初期値を表示する（質問⑥・⑦）。
- 切替時の確認ダイアログは出さない。未確定入力は破棄する。
- 生成sourceの切替時の具体的テンプレート、必須未入力時の仮生成コードは、コネクタ詳細設計・技術検証で決める。空欄から実行可能コードが生成されるとは仮定しない。

### 6.2 アクション詳細設定・確定（質問⑧・⑩）

- ユーザーが入力を変更するたび、**下書き値をセルmetadataへ記録**する。ただし生成Python sourceには反映しない。
- 下書き値が `.ipynb` ファイルに永続化されるのは通常のNotebook保存操作時。自動ディスク保存を独自に実装するという意味ではない。
- 「確定」を押すと入力値を検証し、成功時に確定済み設定をmetadataへ反映し、Extension Hostがsourceを生成・更新する。
- 検証NG時は該当入力欄の直下にエラーを表示する。確定済み設定とsourceを変更しない。下書きは残す。
- Python sourceを直接手動編集してもフォーム値へ逆反映しない。次のフォーム確定時にはフォーム設定から再生成しsourceを上書きする（質問⑪）。上書き前の独自確認は設けない。

### 6.3 状態遷移（概念）

```text
[Pythonセル]
    └─ コネクタ/アクション選択 → [処理セル：アクション初期状態]
       ├─ フォーム編集 → [下書きあり（metadata更新、source不変）]
       │   ├─ 確定NG → [入力エラー表示、下書き維持]
       │   ├─ 確定OK → [設定とsource更新、未更新]
       │   └─ アクション切替 → [以前の下書き破棄、新アクション初期化]
       ├─ アクション切替 → [以前の確定値も破棄、新アクション初期化]
       └─ Python選択 → [Pythonセル：一時退避した元コードがあれば復元]

[未更新] ─ Jupyter標準の再実行成功を検出 → [更新済み]
```

注意：選択だけでsourceを再生成する全体設計と、詳細フォーム確定までは引数を反映しない方針は両立させる。選択時の生成はアクションの初期値・未設定状態からの生成、確定時の生成は確定パラメータを使う。生成できない未設定状態の扱いは未決定。

## 7. 「未更新」状態

- 表示位置：フォーム上部（質問⑨：A）。
- フォームで設定を確定してsourceが変化した後、次の標準セル実行成功まで表示する。コネクタ/アクション選択によるsource変更も同様に扱う。
- 下書き編集のみでsourceを変更していない場合の「未更新」表示は、生成コードの意味では未更新対象に含めない（下書き表示が必要かは未決定）。
- 前回のJupyter標準実行結果はそのまま残す。実行失敗時は「未更新」を解除しない。
- 元sourceの手動編集、Notebook再オープン時の状態推定、実行成功イベント取得方法は要検証。再オープン時に確実な実行状態を推測しない。
- Python実行エラーはNotebook標準の表示に委譲する。

## 8. metadata保存・復元

### 8.1 所有権

| データ | 保持先 | 復元方針 |
|---|---|---|
| 現在のセルモード・connector・action | セルmetadata | `.ipynb`から復元 |
| アクション確定済み設定 | セルmetadata | 復元 |
| 編集途中の下書き設定 | セルmetadata | Notebook保存済みなら復元（質問⑩：B） |
| Python生成コード | セルsource | 通常コードとして残る |
| 元Pythonコードの退避 | Extension Hostの一時メモリ | 同一Notebookを開いている間のみ |
| 実行結果・Python例外 | 標準Notebook出力 | Jupyter標準仕様に従う |
| Python変数・DataFrame・インスタンス | Jupyterカーネル | Notebook metadataには複製しない |
| 未更新の一時状態 | Extension Hostの一時状態 | 詳細復元方法は技術検証待ち |

### 8.2 構造の概念（フィールド名・バージョンは仮案）

```json
{
  "zizai": {
    "cellRole": "action",
    "connector": "CSVConnector",
    "action": "read_csv",
    "committedParams": { "file_path": "data/old.csv" },
    "draftParams": { "file_path": "data/new.csv" }
  }
}
```

上記キー名、キーの欠落・空値の扱い、スキーマバージョン、移行方式は未決定。**下書きと確定値を区別できること**を仕様要件とする。実装時はmetadataの名前空間競合を避ける。

### 8.3 切替・保存時の注意

- アクション切替時は以前のアクションの設定履歴を保持しない（確定済み・下書きとも破棄）。
- 下書きmetadata更新によってNotebookが未保存状態になることは許容する。実際のdirty表示、Undo履歴、保存時の整合性をAPIで確認する。
- 拡張機能のメモリ上の元Pythonコードはmetadataに入れない。

## 9. エラー・通知

| 発生個所 | 表示・扱い |
|---|---|
| フォーム必須・範囲等の検証NG | 入力項目直下にエラー。確定処理を中止 |
| フォーム部品の描画・操作失敗 | UIまたはVS Code標準通知で伝える。具体的な通知区分は未決定 |
| metadata/source更新失敗 | Extension Host側がエラー処理し、既存コードを不用意に破壊しない。ユーザー通知形式は詳細実装で定義 |
| ファイル選択などホスト連携失敗 | Extension Host側で検出し、UIに伝達。OS操作をRenderer側に置かない |
| Python実行例外・実行結果 | Jupyter標準セル出力・例外表示。Node.jsへの例外橋渡し通知は初回実装しない |

## 10. Extension Hostとの概念インターフェース

| 方向 | イベント/情報 | 責務 |
|---|---|---|
| UI → Host | `selectModeOrAction`（概念名）：セル識別子、Python/connector/action | 選択反映、metadata更新、必要なsource・初期化セル更新 |
| UI → Host | `editDraft`（概念名）：セル識別子、下書きフォーム値 | 下書きmetadata更新。sourceは不変 |
| UI → Host | `commitParams`（概念名）：セル識別子、入力値 | 検証結果を踏まえ確定設定保存・source生成 |
| UI → Host | `browseRequest` 等：対象フィールド、選択条件 | ファイル/フォルダ選択などOS連携 |
| Host → UI | 選択候補、フォーム定義、確定値、下書き値、状態、エラー | 表示・復元・メッセージ提示 |
| Host → Notebook | セルmetadata編集、Python source更新、初期化セル生成 | VS Code Notebook編集APIで実行 |
| Notebook → Jupyter | 標準Python source | 標準実行のみ |

メッセージ名、シリアライズ形式、セル識別子、非同期競合時の応答整合性は仮称・未決定。Extension HostがPythonコードを生成し、Rendererは生成しない。

## 11. 技術検証が必須の項目

1. **サイドバー方式の適合ゲート**：Python実行前から対象セルのフォームをサイドバーに表示し、標準のsource・出力と共存できることを確認する。対象切替、非表示・再表示、実行後の表示、セル移動・削除・Notebook切替時の誤適用防止を検証する。セル内HTMLフォーム常設を今回の採用条件にせず、旧調査の未実施結果も合格に変更しない。
2. VS CodeとKiro IDEで同一UIとNotebook編集APIが機能するか。
3. 入力ごとのmetadata更新、dirty/Undo、保存・再オープン・下書き復元が標準Notebook動作と整合するか。
4. コネクタ/アクション切替直後のsource更新、確定時のsource更新、Jupyter標準実行・Run Allの整合性。
5. 「未更新」の実行成功検出が独自Python実行処理なしに可能か。実行後フォーム状態の維持。
6. 初期化セル識別、重複防止、セル移動・複製・削除・Undoとの整合性。
7. 元Pythonコードの一時退避キーがセル移動・削除・複製で混同されないか。
8. NodeFormのサイドバーでの読み込み、CSS隔離、イベント・ファイル選択連携、VS Codeテーマへの追従。
9. 入力中の文字ごとのmetadata更新に伴う性能・Undo増加。必要な場合は遅延保存などを要検討するが、本書では方式未決定。
10. 自作Pythonライブラリの参照、各コネクタ依存、Jupyter標準実行の結果/例外表示（全体設計の結合検証）。

## 12. 決定事項（質問1〜12）

| 質問 | 決定 |
|---|---|
| ① | 通常Pythonと各コネクタの処理を1つのメニューから選ぶ。共通選択UIはセル側に残す |
| ② | 詳細フォームはサイドバーに置き、対象セルに対応するフォームを表示する（2026-10-22変更） |
| ③ | 表示中の詳細フォームは展開。独自折りたたみなし。サイドバー自体の開閉はIDE標準に従う（2026-10-22変更） |
| ④ | Pythonコード欄は常時表示。標準折りたたみのみ |
| ⑤ | 選択欄に通常Pythonを含め、Python選択時はアクション不要 |
| ⑥ | 未確定入力を残したまま切替時、下書きを破棄し即時切替。確認なし |
| ⑦ | アクション切替時は以前の確定済み設定も保持しない |
| ⑧ | フォーム確定時に検証。エラーは該当項目直下、source非更新 |
| ⑨ | 「未更新」ラベルをフォーム上部に表示 |
| ⑩ | **下書き入力もmetadata保存・Notebook再オープンで復元**。sourceへの適用は確定時のみ |
| ⑪ | 生成Pythonの手動編集可。フォームへ逆同期しない。次回確定時に生成コードで上書き |
| ⑫ | 初期化セルは通常Pythonセル。選択プルダウン・詳細フォームをいずれも表示しない |

## 13. 未決定事項（質問12件とは別の技術・詳細事項）

- 1つの共通メニューで通常PythonとPythonコネクタの処理を区別する、正確なラベル表現。
- 通常Pythonセルにも選択UIを常時表示する技術的な方法。初期化セルには非表示とすることとの整合。
- 選択直後の未設定アクションについて、どの範囲までPython sourceを生成できるか。
- 下書き編集のみの表示、対象セルの開き方・切替・通知は[承認済みのサイドバー設計](../features/notebook-sidebar.md)に従い、正式契約と実機での適合を確認する。
- metadata正式キー、バージョニング、フォーム定義の配置、イベント形式、重複セル識別方式。
- 再オープン後の「未更新」復元と実行成功イベントの取得方式。
- UIホスト連携・非入力検証エラーの通知形式。
- Zizai-formの再利用方式・ライセンス確認・依存導入方式。

これらはヒアリングで勝手に確定したものではない。実機API検証、基本のUI実現可能性確認、および後続詳細設計で具体化する。
