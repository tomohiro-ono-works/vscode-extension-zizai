## 1. 分類・環境・結果の記録

CLIから起動したか、VS Codeを起動したかでは分類しない。実際にAPIを呼んだのか、画面要素を自動操作したのか、ユーザーがUIを操作したのかをケースごとに記録する。

- 単体／API・結合：エージェントが準備・実行・証跡採取・分析・記録を担当する。
- UI自動：Playwrightを使う方針。候補ケースの範囲・開始方法・開始担当は事前合意が必要で、現時点では未合意。内部状態の直接変更やJavaScriptのイベント発火を、クリック・キー入力を通した証拠にしない。
- 手動UI：ユーザーはUI操作と短い報告、エージェントは環境・架空データ・採取・分析・記録を担当する。ユーザーへターミナル操作、設定編集、ログ整理を依頼しない。
- 文書・証跡の静的照合は製品テストと別枠で記録する。実機で実行したAPIテストも手動UIの合格へ移さない。

各ケースには対象ソースcommitと未コミット差分、実行機・OS・アーキテクチャ・Python／Node／VS Code・関係拡張版、前提の充足根拠、操作主体・実際の操作経路、期待結果・実際の結果・終了値・証跡参照を記録する。判定は合格／不合格／未実施／対象外とし、対象外の理由、モックや省略の範囲も残す。APIとUIで同じ処理を通しても結果は別ケースである。

環境区分は次のとおり。対象版は準備時に固定し、観測した版を最低対応版や全環境の保証へ広げない。

| --- | --- |
| E-DOC | 対象checkoutと固定版の仕様・JSON／TOML。ネットワーク・GUI・実データに依存しない静的確認 |
| E-API | 対象checkout、既存runner、固定依存を導入した専用環境。ビルド用Pythonは -I でもbackendとpipを参照できること。既存Notebookカーネルは変更しない |

3. 006-04：受領済みコマンドのCI対象を先に設計する。006-03全体完了は不要。対象実装とコマンド・固定依存が揃い、CI編集の作業権限を満たした単位でworkflowへ接続する。
4. 006-05：ZIPの本検証は必要成果物・統合／CI結果を受領してから行う。配布記録・収録条件の設計は並行できる。

005-04の現在の独立単位の入口は次の固定版で実在を確認した。これは当該コードを含むcheckoutで使う既存の手順で、この006ブランチで実行済みという意味ではない。

~~~text
参照commit: e207d3f59e49905e0e786a5301d55cbb56b0465e
npm --prefix scripts/contracts ci --ignore-scripts
node --test tests/contracts/values.test.mjs tests/contracts/assets.test.mjs
node scripts/contracts/cli.mjs generate --source-commit e207d3f59e49905e0e786a5301d55cbb56b0465e
node scripts/contracts/cli.mjs check --source-commit e207d3f59e49905e0e786a5301d55cbb56b0465e
~~~

CIでは対象checkoutの実在するcommitを明示してsource照合する。入力変更後に古い固定commitを流用しない。generate→check→消費を直列化し、checkが失敗した資産を梱包しない。単体とAPI・結合をケース内訳で分け、上記の混在runner全体をUI自動テストと呼ばない。UI自動は今回CI実装・実行しない。
