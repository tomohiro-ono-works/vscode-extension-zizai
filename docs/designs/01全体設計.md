# VS Code拡張機能｜全体基本設計

更新日：2026-10-22

対象：VS Code / Kiro IDE 上の Jupyter Notebook（`.ipynb`）  
位置づけ：全体構成・各層の責務・境界I/F・リリース範囲の基本設計。コネクタ／UIの詳細要件は個別設計で扱う。

> **状態の区別**：本書の「確定」は今回のヒアリングで合意した設計方針を指す。既存の `extension.js` / `renderer.js` の実装完了や、VS Code / Jupyter APIでの技術検証完了を意味しない。各コネクタMarkdownは別製品／既存実装の調査資料であり、新拡張機能への実装完了や仕様採用を意味しない。

2026-10-22、利用者は詳細フォームをサイドバーに配置する方針を選択した。[配置変更の決定](../decisions/2026-10-22-notebook-sidebar.md)に基づき、セル内常設を前提とした配置条件を更新する。対象セルの切替・表示・保存の具体案は[サイドバー設計案](../features/notebook-sidebar.md)でレビューする。製品の実装・サイドバー実機適合を確認した意味ではない。

## 1. 目的と基本原則【確定】

- Jupyter Notebook の標準機能を保持したまま、セルで処理を選択し、フォームの設定から通常の Python コードを生成する。
- 「Python / Data / SQL」は処理の例示であり、固定の3機能・3種類だけを提供するという設計ではない。処理はコネクタ／アクション単位で拡張する。
- UIは入力・表示、VS Code Extension Host（Node.js）はセル操作・設定管理・コード生成を担当する。
- 実行は既存 Jupyter Python カーネルへ任せる。独自カーネル、独自実行サーバー、Node.js–Python間のDataFrame同期は作らない。
- Jupyter標準のセル実行・Run All・結果表示・Python実行エラー表示を利用し、重複実装しない。
- KISS原則に従い、標準APIと少数のコンポーネントで構成する。
- 個別コネクタ／UIコンポーネントの引数・出力・レイアウト・内部処理は別チャットで定義する。

## 2. 全体構成【確定】

```text
VS Code / Kiro IDE
└─ Jupyter Notebook (.ipynb)
   ├─ UI層：HTML / CSS / JavaScript
   │  └─ セル側の処理選択、サイドバーの詳細フォーム・入力・確定
   ├─ 拡張機能層：Node.js + VS Code Notebook API
   │  └─ UI通信、設定・metadata管理、Pythonコード生成、セル更新
   └─ Jupyter標準実行基盤
      └─ 既存Pythonカーネル（Notebookごとの選択カーネル）
         ├─ 生成された初期化セル：importとインスタンス生成
         ├─ 生成された処理セル：既存インスタンスのメソッド呼出し
         └─ 自作Pythonライブラリ → 各コネクタ

標準Notebookセル出力：実行結果・Python例外の表示
```

- Node.jsは業務データ処理・Python実行を担当しない。
- Python変数・DataFrame・インスタンスは選択された既存カーネルの名前空間に保持される。拡張機能はカーネル間の分離・共有を独自制御しない。
- importは拡張機能の裏側で実行しない。セルのsourceにimport文を生成し、Jupyter標準の実行で評価する。

## 3. 各層の責務【確定】

| コンポーネント | 主な責務 | 責務外 |
|---|---|---|
| UI（セル側の選択UI・サイドバー） | 処理選択、フォームの表示・入力、確定イベント | Pythonコード生成、業務処理 |
| Extension Host（Node.js） | UI通信、フォーム状態とセルmetadata管理、生成コード作成・セルsource更新、初期化セル管理 | Jupyter実行、DataFrame処理 |
| Notebook（`.ipynb`） | セルsource・metadata・標準出力の保存媒体 | 独自実行エンジン |
| Jupyterカーネル | セルのPython実行、Python変数・インスタンス保持、標準出力・例外 | UIフォーム管理 |
| 自作Pythonライブラリ | 処理呼び出しの基盤、共通ロジック | Notebook API操作 |
| コネクタ | 各アクションの個別処理 | セルの生成・表示・管理 |

## 4. 境界I/Fの基本方針【確定：概念レベル】

| 境界 | 渡すもの | 方針 |
|---|---|---|
| UI → Extension Host | 処理識別子、入力設定、選択／確定イベント | UIはPythonコードを作らない |
| Extension Host → UI | 保存済みフォーム設定、UI表示に必要な情報 | 表示・操作のための情報のみ |
| Extension Host → Notebook | セルmetadata、生成したPython source | 編集APIを利用し、設定選択だけで実行しない |
| Notebook → Jupyter | 通常のPythonセルsource | 標準の▶／Run Allに委ねる |
| 生成Python → Pythonライブラリ | import、インスタンス作成、メソッド呼出し、設定値 | 通常のPythonコードとして実行 |
| ライブラリ → Jupyter | Python戻り値、オブジェクト、例外 | Node.jsへDataFrameを同期しない |
| Jupyter → Notebook出力 | 標準の実行結果・Pythonエラー | 独自表示UIは初回対象外 |

> 関数シグネチャ、JSON Schema、メッセージ形式、パス解決方式は詳細設計で決める。本章はそれらを先に拘束しない。

## 5. セル生成・初期化セル【確定】

1. ユーザーがセルでコネクタ／処理を選ぶと、拡張機能は必要なPythonコードを生成する。
2. 必要な初期化セルがなければ、Notebookの先頭に**コネクタごとの独立した通常のPythonセル**を生成する。
3. 同じコネクタの初期化セルが既にあれば再利用し、重複生成しない。
4. 初期化セルにはimportとインスタンス生成を記載し、処理セルには既存インスタンスのメソッド呼出しを記載する。
5. 初期化セル・処理セルとも生成／設定だけではPythonを実行しない。Run AllではNotebookの並び順に標準実行する。単独実行では利用者が必要な初期化セルを先に実行する。
6. CSVやSQLなどの入力ファイルは処理セルの実行ごとに読み直す。インスタンスの再利用とファイル再読込は別の責務とする。
7. セル削除とUndoはNotebook標準機能を利用し、独自の復元機能は作らない。

概念例（API名は仮称）：

```python
# Notebook先頭：CSVコネクタ初期化セル
from zizai import CSVConnector
csv = CSVConnector()
```

```python
# 別々の処理セル
_df_sales = csv.read('sales.csv')
```

```python
_df_customers = csv.read('customers.csv')
```

上記の名前・コードは説明例であり、正式なAPIや出力変数名を定義しない。

## 6. UI入力と反映タイミング【確定】

- **コネクタ／処理の選択**：確定ボタン不要。選択時にUIと必要な生成コードを反映する。
- **コネクタ内部の設定**：入力後、確定ボタンでセルmetadataと生成コードへ反映する。
- **実行**：選択や設定確定だけでは実行せず、Jupyter標準の▶／Run Allを使用する。
- **Notebookファイル保存**：通常のNotebook保存操作（例：`Ctrl + S`）に従う。
- コード生成の所有者はNode.js側。UI側のJavaScriptは設定値を送り、Notebook sourceを直接作らない。

## 7. 設定・実行状態の所有権【確定】

| 対象 | 主たる保持先／担当 | 補足 |
|---|---|---|
| セルの処理種類・フォーム設定 | セルmetadata | `.ipynb`の通常保存に従う |
| 生成されたPythonコード | セルsource | 通常のPythonコードとして残る |
| Python変数・DataFrame・インスタンス | Jupyterカーネル | 別途Node.js側へ複製しない |
| 実行結果・Pythonエラー | Notebook標準出力 | `.ipynb`標準仕様に従って保存され得る |
| 切替前の元Pythonコード | Extension Hostの一時メモリ | Notebookクローズ時に破棄し、永続バックアップは作らない |
| 「未更新」表示など作業中の状態 | 拡張機能の一時状態 | 再オープン時の詳細復元方式は別途検証 |

- Notebookごとのフォーム設定・拡張機能状態は独立させる。カーネルの変数共有についてはJupyterの標準挙動に従う。
- フォーム設定を変更した後も前回の結果は残し、「未更新」を表示する。再実行に成功した場合に更新済みへ戻す。外部ファイルの変更監視は行わない。
- 元コードの一時退避と復元は、同じNotebookを開いている作業中のみ扱う。Notebookを閉じた後の復元は保証しない。
- セル出力データが`.ipynb`に一切保存されない保証はしない。標準Notebookが出力を保存する仕様と矛盾させない。

## 8. 実行・エラー・結果表示の責務【確定】

```text
処理選択 → フォーム設定／確定 → Node.jsがコード生成 → Notebook source更新
                                                           ↓
                                         Jupyter標準の▶／Run All
                                                           ↓
                                  Pythonライブラリ／コネクタ実行
                                                           ↓
                              Jupyter標準の実行結果・例外表示
```

- Jupyter標準の実行順序、停止・エラー表示へ委ねる。拡張機能独自のRun All実装、Python例外のNode.jsへの橋渡し通知は初回対象にしない。
- フォーム検証・コード生成・セル更新時のエラーは拡張機能側で扱う。Python実行中の例外はJupyter側で扱う。
- **独自の結果表示UIおよび100行単位のテーブルページネーションは優先度低い**。初回ではJupyter標準の結果表示を使用する。

## 9. 配布・導入・バージョン【確定】

| 論点 | 方針 |
|---|---|
| 配布 | VS Code拡張機能と自作Pythonライブラリを1つのZIPで配布 |
| 展開先 | 利用者が任意の場所へ展開できる |
| セットアップ | 利用者が手動で行う |
| Python実行環境 | 既存Jupyterカーネルを利用 |
| Pythonライブラリの利用範囲 | フォーム経由を正式サポート。通常Pythonセルからの直接利用は禁止しないが公開API互換性を保証しない |
| バージョン | 拡張機能とPythonライブラリを個別管理する方針 |
| 初回リリースの互換性チェック | 実装しない。実行時エラーを基本とする |
| 初回リリース後 | バージョン管理・互換性チェック機能を追加検討 |

ZIPを任意の場所へ展開した際のライブラリ参照方法、拡張機能の導入手順、Python依存ライブラリの導入手順は技術・詳細設計で確認する。

## 10. リリース区分【確定】

### 10.1 初回リリース：Notebook共通機能（7項目）

- セル内の処理選択・切り替え
- 対象セルの処理に応じたサイドバーフォームUI表示
- フォーム設定からPythonコード生成
- コネクタ初期化セルの自動生成・再利用
- Notebook設定（metadata）の保存・復元
- 設定変更後の「未更新」表示
- セル切り替え前のPythonコードの一時退避

### 10.2 初回リリース：コネクタ（7種類）

- CSV
- Excel
- DuckDB
- BigQuery
- Python
- Data Integration
- Shell

### 10.3 次回リリース：コネクタ（3種類）

- Plotly
- Chrome
- Windows

Notebook共通機能の次回リリース指定はなし。

### 10.4 優先度低い

- 独自の結果表示UI
- 実行結果テーブルの100行ページネーション
- Vectorコネクタ
- Seleniumコネクタ

### 10.5 Jupyter標準機能（独自実装しない）

- セル実行・Run All
- Python実行結果のセル内表示
- Python実行エラーの表示

これらは初回リリースの**結合検証対象**とする。

## 12. 実装・技術検証が必要な事項【未確定】

- サイドバーのフォームと対象Notebook／セルの対応、表示切替・非表示からの復元、標準のPythonコード欄・セル出力との共存。フォーム描画はPython実行を前提とせず、対象セルの切替と実行後の表示・下書き維持を検証する。セル内HTMLフォーム常設を製品実装の成立条件にしない。
- 初期化セルの識別・位置の判定、重複抑止、セル移動・複製への対応。
- Notebookセル切替前のコードを一時メモリと正しく対応付ける方式。
- 任意のZIP展開先から自作Pythonライブラリを利用する方式。
- 既存Pythonカーネル上で生成コードを実行した際の依存ライブラリの解決。
- Notebook標準のRun All、エラー停止、出力表示との結合動作。
- VS CodeとKiro IDEでのNotebook API互換性。
- コネクタ・アクションごとの入力、戻り値、例外、フォームUI、生成コードの具体仕様。
- 将来の独自結果表示・ページネーションの通信方式（低優先度）。

未確定事項は、ヒアリングで確定していない事項とAPI制約による実機検証事項を含む。ここから詳細仕様を推測して確定しない。

## 13. 現行試作と設計変更の扱い

2026-10-17版のDESIGN.mdでは、`extension.js` / `renderer.js` によるセル種類切替、Data/SQLフォーム、ファイル選択、metadata保存、CSS分離が**試作段階**と記載されていた。今回、新コードの動作試験は実施していないため、実装済み判定は更新しない。

旧文書からの主な設計変更：

1. Python / Data / SQLの固定分類から、処理を選択する共通セルUIへ変更。
2. コネクタ単位の初期化セルをNotebook先頭に生成・再利用する方針を追加。
3. コード生成の責務をNode.js、実行とPythonエラー表示をJupyterへ明確化。
4. コネクタ内部の設定には確定ボタンを設け、コネクタ選択には設けない。
5. 独自結果表示・100行ページネーションを低優先度へ変更。
6. 12コネクタを初回7／次回3／低優先2に区分。
7. ZIP同梱・任意配置・手動セットアップ・個別バージョン方針を追加。

旧文書にあったCSV/Parquet/Excel/JSONのData専用フォーム、SQLファイル専用フォーム、Polars固定などの個別処理仕様は、今回の全体設計として一律に確定させず、それぞれのコネクタ詳細設計で扱う。
